## 二、分工：機械那一半 vs 模型那一半

| 誰 | 做什麼 | 為什麼 |
|---|---|---|
| 機械演算法（Earley 文法） | 算出「寫到這裡，下一個合法的 token 有哪些」（關鍵字、符號、名詞、字面值），過濾掉不合法的、宣告類的、不屬於這個語言的 | 可靠、便宜、不會幻想不存在的語法 |
| 機械（自動補） | 只有一個合法選項就直接補（`def f(...)` 後的 `:`、`{`），不問模型 | 省呼叫 |
| 模型（開思考） | 在過濾後的選項裡做選擇題（A／B／C…）；要新名稱、數字、字串字面值才寫一小段 | 使用者的前提：0.6B 開 thinking 做選擇題很精準 |
| 設計樹與思考堆疊 | 名詞（變數、函式、類別成員）從作用域與計畫簽名／UML 選；每一題的題目帶焦點標頭（目標、路徑、已定的簽名） | 讓選項有語意，不只是語法合法 |

## 三、每種語言一份獨立的文法（已實作並測試）

`renderer/src/recipe/grammar_core.js`：Earley 解析器（處理可空規則）＋六種語言各自的語句級文法：**python、c、cpp、java、csharp、nodejs**。每個語言各自編譯、各自快取，執行時彼此隔離（沒有「clike 家族」）。ruby、perl、bash、組語沒有文法，一律自由寫。

- **不共用的證據（測試）**：C 的合法 token 沒有 `as`／`is`／`instanceof`（我第一版共用文法時，C 的選項裡出現了這三個——使用者一眼指出的問題）；Java 有 `instanceof`、沒有 `as`／`is`、沒有指標／`sizeof`／`::`；C# 有 `is`／`as`、沒有 `instanceof`；`->`／`sizeof` 只有 C／C++；`::` 只有 C++；Python 不接受大括號／`i++`／`&&`／`?:`；JS 不接受型別宣告。
- **正面語料**：Python 20 個種子程式的每條邏輯行；C／C++／Java／C#／JS 各自的真實程式（struct、陣列、`for`／`switch`、泛型、增強 `for`、`foreach`、箭頭函式、解構、`std::`、正則字面值…）。
- **別的語言只能在字串或註解裡**：詞法把字串、註解視為不透明（SQL、HTML、別的語言的程式碼放在字串裡都不影響解析）。
- **內嵌組語屬於 C／C++ 各自的 CoLU**：C 與 C++ 的文法各自有 `asm`／`__asm__`／`__asm`（GNU 擴充：樣板字串、輸出／輸入／clobber 清單），`#pragma` 是前處理行；其他語言的文法沒有這些關鍵字。寫程式時預設**不給** asm 選項（機械丟掉），任務明說要內嵌組語（`opts.allowInlineAsm`）才開。組語語言本身（asm-x64／asm-x86）是獨立的語言，不是內嵌。
- 吃不下合法程式時（文法有洞）：呼叫端以編譯器的位置為準，文法預測只是加分的來源（語法修復就是這樣用）。

誠實的範圍：語句級的**子集**文法，不是完整語言規格（沒有 C++ 模板／巨集、Java 註解、Python f-string 內部、裝飾器參數細節…）。

## 四、文法引導寫作（已實作並測試；真模型數字見第七節）

`renderer/src/recipe/guided_write_core.js` 的 `guidedWriteFunction`：一個函式一個函式地逐 token 寫。標頭（簽名）由程式放進去、文法驗證；每一步：

1. Earley 算出合法終端 → 機械過濾（每種語言各自的丟棄表：函式本體不會出現的宣告類關鍵字）→ 各語言各自的先驗排序。
2. 只有一個合法選項 → 自動補。
3. 選項不多（≤14）→ 一層扁平選單；否則分類別兩層（關鍵字／名稱／字面值／符號／換行）；每頁 8 個＋「更多」。
4. 名稱選項 = 局部變數（最近宣告的在前）→ 「✍ 新名稱」→ 計畫的函式 → 設計樹的符號 → 內建名稱；`.` 之後是常見成員名。標準函式庫的 `#include`／`import` 由程式依用到的名稱補。
5. Python 的縮排是選擇題：「進入下一層／同層／退回第 k 層／函式寫完了」，不會憑空多縮或少縮。
6. 模型選不出來（回 null）→ 這個函式退回自由寫並記 gap（不亂挑）；`free` 寫出不合法的名稱／數字會被拒絕。

**上限以一個函式為單位**（`maxSteps`、`maxChoices`）；開發期間預設 `Infinity`（使用者要求），profile 之後再訂（例如 300／900）。

### 機械那一半的驗證（神諭選擇器）

測試用「神諭」代替模型：它知道目標程式，但**只能從文法給的合法選項裡挑**。能走完＝文法的合法選項涵蓋了目標的每一步；走不完＝文法有洞（這個測試抓出了好幾個洞：`System.in`、`new[]`、切片 `[::-1]`、`typedef struct {...}`、菱形 `<>`、`foreach`、`(const int*)` 轉型、`sizeof(type)`、賦值左邊必須是可賦值的目標…）。

- **Python：20 個種子程式的每個函式（21 個）都能由神諭走完；組起來用真的判題器全部 AC。**
- c／cpp／java／csharp／nodejs：各自的函式，輸出與目標逐 token 一致。
- 這**不是模型能力的證據**，只證明機械那一半是對的。
- **成本發現**：神諭走這 21 個函式，平均每個函式 **173 次選擇題**（含翻頁與分類別那一層）、12.6 次「自己寫」。如果每題都開思考（真模型約 13 token/s），一個函式要上小時。這是 profile 要處理的第一個問題（見第七節與下面「可能的省法」）。

### 兩種「模型挑選」策略（2026-11-06 加入第二種）

| 策略 | 模型怎麼參與 | 實作 |
|---|---|---|
| `choose`（使用者原本的設計） | 合法選項做成 A／B／C…，模型（開思考）回字母 | `makeBackend().choose`；答案若等於某個合法選項的**內容**（`+`、`total`）也算選了它（別名）；字母優先 |
| `rank`（約束解碼） | 合法選項由文法機械算好；模型對每個合法選項用**下一個 token 的機率**打分，取最高。不需要回字母 | `FaGuidedWrite` 的 `lm` 游標（`openCursor`：KV 快取、`rank`、`commit`、`greedy`）；目前只有評估用的原生適配器（`scripts/eval/native_gen_adapter.js`）實作了游標 |

為什麼加第二種：第一批真模型實測顯示，0.6B 用字母選擇題的**格式本身就不穩**——不開思考時回 `{"pick":"+"}`、`{"pick":"-2"}`、`{"pick":"letters"}`（回了選項的內容或自己的詞，不是字母），開思考時第一題選錯類別、回 `{"pick":"split"}`，每題 30～60 秒。`rank` 讓模型做它最擅長的事（預測下一個 token，和它自由寫程式時一樣），文法只負責讓不合法的 token 沒有機會被選到。兩種策略都保留，用同一批題目對照（見第七節）。

`rank` 的細節：當前行已寫的部分當基底（行首空白併進候選，分詞邊界才自然——`    return` 要合成 `   `＋` return`，分開 tokenize 會被誤判成低機率）；已完成的行才提交進 KV 快取；多 token 候選只對第一 token 分數最高的前 8 個再跑額外前向；新名稱／數字／字串用模型自己的貪婪續寫取一個字面（驗證過才當候選）；Python 的換行與縮排（`⏎ 同層`／`⏎ 進入`／`⇤ 退回第 k 層`／`■ 寫完`）也是候選，用 `\n`＋縮排的字串打分，函式結尾用 `\n```` 打分。

測試用的「假語言模型」（知道目標答案、只對合法候選打分）驗證機制：Python 的函式與 20 個種子程式的每個函式都走得完、組起來 AC、**一個函式只開一次游標**、沒有任何字母選擇題。這不是模型能力的證據。

## 五、每種語言各自的 CoLU 集合（已實作並測試）

`renderer/src/recipe/lang_colu_core.js`（資料）＋ `plan_core.js`（按語言篩選）：

- 每個語言一份集合：寫作方式（`guided`／`free`、是否支援專案模式）、能力（`local_write_code_<語言>`，每個語言一條不同名的工具）、**自己的失敗規則**（regex＋動作）、給模型的語言規則文字、工具鏈資料（檢查／執行／除錯器名稱）、`inlineAsm`（只有 c／cpp）。
- `plan_core`：CAPS 項目有 `langs` 欄位，`buildPlan(goal, facts, {lang})` 只看這個語言的能力；**沒有指定語言就沒有計畫**（不亂猜）；`decideFailure` 先判斷這個語言自己的規則，別的語言的規則看不到（python 的縮排錯誤→retry，C++ 看不到這條；C／C++ 段錯誤→abort，因為需要 gdb／valgrind 的除錯步驟，尚未實作）。
- 同一個目標「寫程式」，python 得到 `local_write_code_python`、C++ 得到 `local_write_code_cpp`、ruby 得到 `local_write_code_ruby`（標籤說明各自的寫法）。宿主（`floating-assistant.js`）為每個語言各註冊一個本機函式，計畫的 facts 帶 `lang`。
- 迴圈寫函式時，規則文字取自這個語言自己的集合；有文法（`grammar:true`）且呼叫端給了 `choose` 才走引導，否則自由寫。

誠實的範圍：失敗規則目前只管「寫程式這一步」的失敗；除錯器步驟（gdb／pdb／jdb…）未實作；專案模式（UML→逐類別）的類別本體仍是自由寫（文法只涵蓋函式層，類別層沒有引導）。

## 六、語法修復也走同樣的方法（已實作並測試）

`syntax_fix_core.js`：編譯器報錯位置 → **文法分析**（錯誤所在的最上層項目／邏輯行，算出該位置合法的下一步）→ 候選（插入合法的關鍵字／符號、補作用域已知的名稱、換掉／刪掉不合法的標點）→ **文法預檢**（套用後文法要能往前多吃幾個 token，機械過濾）→ 語意排序（識別字黏合、引數個數、printf 格式…）→ 編譯器驗證 → **模型（開思考）在過濾後的選項裡做選擇題**。我手寫的備援詞彙（每種語言各自一份）只在文法不可用或與編譯器位置不一致時補足。

整個過程留下可讀的紀錄（`trace`／`formatTrace`）：編譯器怎麼說 → 文法在哪個 token 判定出錯 → 這個位置合法的關鍵字／符號／名詞 → 候選（標明來源是文法還是備援）→ 驗證結果 → 誰選的、選了哪個。

收尾類符號（`; ) ] } , :`）緊貼前一個 token 後面，其餘插在文法判定的位置。評估數字見 DESIGN.code-repair.md。

### 可能的省法（profile 之後再決定，目前都沒做）
- 「新名稱」之外，把「同一個語法位置合法集合很大」的步驟改成先讓模型自由寫一行（便宜），文法只在**不合法的 token** 才介入、用選擇題修（這就是語法修復的機制）；

## 八、限制與沒做的事
- 文法是子集；沒有文法的語言（ruby、perl、bash、組語）沒有引導，只能自由寫＋備援詞彙修語法。
- 引導寫作只到函式層；專案模式的類別層沒有。
- 真模型的選擇題準確率還沒有整批數字（見第七節）；第一題的觀察是：開了思考，模型在「現在要寫哪一類」這一題選錯了。
- 步數上限開發期間是無限大；profile 前不要把它當產品行為。
