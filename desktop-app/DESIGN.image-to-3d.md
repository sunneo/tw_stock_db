## 結論（先說）
1. **UniK3D 有官方的 ONNX 匯出程式，但有三個硬傷**：授權是 CC BY-NC 4.0（非商業）；解析度在匯出時就固定（462×630）；沒有現成的 ONNX 檔可下載（要自己匯出）。**在瀏覽器裡能不能跑，我沒驗證。** 這個專案是公開產品，所以「把它內建、替使用者下載」目前不可行，除非你接受非商業授權的限制。
2. **預設引擎建議用 Depth Anything V2 Small**：Apache-2.0（Small 這一個規格；Base／Large 是非商業）、已有 onnx-community 的 ONNX、Transformers.js 現成支援，而且本專案已經有 Transformers.js 的工作執行緒、WebGPU 降級 CPU、模型下載進度那一整套（`renderer/src/vlm/vlm_core.js`），新增一種模型只是加一個登錄項目。缺點：輸出是相對深度（沒有公尺單位）。
3. **你貼的混合架構，離線那一層（Base Layer）可行；雲端精煉那一層，使用者決定改成「本機長時間處理」**（見「已決定」）：不上雲、不內建重型模型，用編輯器＋成功案例（save case）＋離線訓練器累積。
4. **不做浮雕。** 現有的 `image-decompose-redraw` 已經是浮雕（四叉樹三角網格充氣成 2.5D），使用者明說受夠了，新管線不再走這個做法：先分出物件，**每個物件用自己的邊界直接做成封閉的立體**，再依深度細切。單張圖看不到的背面是依輪廓推測的，輸出要寫明。

## 一、UniK3D 的 ONNX（要求的那條路）
**查到的事實**
- 匯出程式存在（官方示範站的 `unik3d/models/export.py`）：`torch.onnx.export`，opset 14；預設包成 `UniK3DONNX`（輸入 `rgbs`，輸出 `pts_3d` 與 `confidence`），另有帶相機光線的版本 `UniK3DONNXcam`。
- 規格：`vits`／`vitb`／`vitl` 三種；輸入 `(B,3,H,W)`，預設 462×630（14 的倍數）；**只有批次軸是動態的，程式自己寫「不支援動態形狀」**；為了能匯出，要關掉 DINO 的高效注意力。
- 權重大小（Hugging Face）：`vits` 的 `model.safetensors` 142 MB，`vitl` 1.44 GB。ONNX 檔大小應該接近，**但我沒實際匯出過，不確定**。
- 輸出是相機座標下每個像素的 3D 點（有公制尺度、支援魚眼與全景），不是網格；要自己轉成網格。
- 官方只測過 Linux＋CUDA 11.8；沒有速度數字。
- 授權：GitHub 說明寫 Creative Commons BY-NC 4.0。Hugging Face 權重頁面這次沒看到授權標示（**未確認**）。

**判斷**
- 只有 `vits`（約 142 MB 級）有機會放進瀏覽器；`vitl` 約 1.4 GB 不實際。
- 固定 462×630 表示直式、橫式圖要補邊或分別匯出，輸出再裁回來。
- 跟 Depth Anything 比：好處是公制尺度與真正的 3D 點；代價是較大、授權較嚴、沒有現成 ONNX、要自己維護匯出流程。
- 進瀏覽器之前必須先驗證（未做）：① 在有 GPU 的 Linux 機器跑 `export.py --backbone vits` 能不能成功；② 匯出檔在 ONNX Runtime Web（WebGPU 與 WASM）每個運算子是否支援、載入是否過大；③ 一張圖的實際耗時（CPU／WebGPU）；④ 權重授權（Hugging Face 模型卡）。

## 二、你貼的混合架構逐項評估
| 項目 | 評估 |
|---|---|

| 單視角深度（Depth Anything V2 Small） | **可行且最省事**（見結論 2）。你寫的 24 MB 級大致吻合（約 2500 萬參數）；輸出是相對深度。 |
| MediaPipe 自拍分割 | 只適合人像，通用物件用不上。 |
| 稜柱擠出＋補洞，做成閉合低模 | **可行，純 JS 就夠**，但**不走「前表面網格再補背面」的浮雕路線**：改成每個物件以自己的遮罩邊界直接做封閉殼（柱體或方塊），再依深度細切，見「封閉策略」。本專案的 3D 編輯器已經吃「自訂形狀」（`polygon` 物件的頂點與面）和既有的 2.5D 網格轉換，輸出直接餵進去即可。 |

| 輸出 .glb | 本專案 3D 編輯器目前**不支援匯入 glb**（設計文件寫「glb 沒做」），支援 STL／OBJ／3MF／FBX。第一版輸出 OBJ 或直接轉 `polygon` 物件，glb 另外加。 |
| 雲端精煉（Zero123++／LGM／TripoSR→高模） | **與「離線」需求衝突**，而且要 GPU 服務與費用。建議不放進這次範圍。 |
| 「全 CPU 離線」的 ONNX 版 Zero123++ 5～30 分鐘 | 我沒驗證這個數字；以現有 VLM 在本專案 CPU 的實測（幾十秒到兩分多鐘）來看，只能當作「理論上可能」。不建議。 |

## 三、做法（2026-10-29 使用者定案：以混合架構為主）
- **基礎層（預設，離線，所有圖片）**：新增「深度」類模型登錄（Depth Anything V2 Small）→ 可選去背（沿用現有或加 MobileSAM）→ 分出物件→每個物件以自己的邊界做封閉殼，再依深度細切（見下一節「封閉策略」）→輸出 `polygon` 物件（或 OBJ），在 `/edit-3d-model` 打開。入口：斜線指令 `/image-to-3d` 與同名工具 `image_to_3d`。
- **景物照片的加強路徑（選用，UniK3D）**：先由視覺模型（VLM）判斷這張圖是什麼。判斷用封閉選擇題（A 景物照片／B 單一物件／C 人像／D 插畫或圖示），答案由程式核對（例如拿不到答案、模型不可用，就當 B，不走這條路）。只有 A 才用 UniK3D 做公制的 3D 點→整個場景可見表面的網格（貼原圖當顏色）。B、C、D 一律走基礎層。
- **UniK3D 不內建、不替使用者下載**：使用者自己取得模型，到「媒體→離線模型」設定頁手動指定檔案；沒設定就不出現這條路，也不提示打擾。設定頁要顯示授權（CC BY-NC 4.0，非商業）的提醒，責任在使用者。
- **精煉層（取代雲端）＝本機長時間處理**：基礎層或景物路徑的結果進編輯器繼續修；做得好的存成**成功案例**（`editor_cases`，種類 `edit-3d`）進離線訓練器，之後相似的圖直接拿案例當起點，只做微調。長時間的工作（例如多張圖、逐步修網格）用背景工作：進度卡片、可中斷續跑。**多視角擴散／3DGS 這類要 GPU 與大模型的精煉不內建**；真要用，由使用者在自己的 GPU 機器跑，輸出 OBJ 匯入編輯器。

### 要先講清楚的缺口（這會影響「手動下載」能不能用）
- **官方只發 PyTorch 權重**（`model.safetensors`），不是 ONNX。使用者「手動下載」得到的檔案瀏覽器跑不了，必須再執行官方的 `export.py` 匯出 ONNX（要 Python 與 PyTorch 環境，固定解析度 462×630）。我沒查到可信任的第三方現成 ONNX（**未驗證**，不要假設有）。
- 所以「媒體→離線模型」的設定頁要做兩件事：① 收一個使用者已匯出的 `.onnx`；② 附一份匯出步驟說明（指令、環境、解析度、`vits` 優先）。匯出本身我們不在 App 裡做。
- 景物判斷用的視覺模型要先存在（現有 Florence-2 等）；沒下載就跳過這條路，走基礎層。

## 封閉策略（使用者 2026-10-29 補充：要有選擇，物件用自己的邊界封閉）
**先分層，再各自處理**：把畫面分成「背景」與「一個個物件」（實例遮罩：人臉、蘋果、杯子…；遮罩來自分割模型，景物照片可先讓視覺模型列出有哪些東西再切）。背景是一整片場景表面；物件各自是一團。

**封閉的選擇（一個參數，使用者可以在要求裡直接說）**
| 選擇 | 做法 | 什麼時候 |
|---|---|---|
| 物件封閉（`objects`，**預設**） | **每個分得出來的物件都是封閉的一團**（人臉、個別物件都算）；背景只是襯在後面的一片，不當成果 | 一般照片：場景中的一顆蘋果，蘋果就是封閉的一團 |
| 全部封閉（`all`） | 背景也做成一塊封閉的板；使用者說「物件要封閉」「要能列印」時，所有物件**統一**封閉，一個都不漏 | 要 3D 列印、要放進別的場景當實心物 |

使用者的話優先於預設：說「蘋果要封閉」就只封那一個；說「物件都要封閉」就是 `all` 的物件部分；沒說就用預設。選擇由程式解析（中文關鍵字＋斜線指令參數），解析不出來才用封閉式選擇題問模型，答案由程式核對。

**物件怎麼封閉（用物件自己的遮罩邊界，不是整張圖的邊框）**
1. **粗殼**：以物件遮罩輪廓為底，沿深度方向做出一個粗的封閉殼。兩種殼，可選或自動挑：
   - **柱體**（cylinder 式）：輪廓沿深度軸擠出，適合圓的、單純的東西（蘋果、杯子、臉）；
   - **方塊**（樂高式）：把物件佔的空間切成大方格，只留被物件占到的格子，外表面就是封閉殼；適合不規則、有凹凸的東西。
2. **細切**：粗殼先封閉了，再由粗到細逐步切細（方格逐層對半、柱體增加輪廓點與段數），每一層都把前表面貼回深度圖，直到面數或誤差達到上限。任何一層都是封閉的，所以可以隨時停下來，這也符合「長時間處理可以中斷續跑」。
3. **厚度（背面深度）是猜的**：單張圖看不到背面。預設用物件自己的寬度乘一個比例，圓形物件接近球狀；若有景物路徑（UniK3D）的公制深度，用該物件前表面的深度範圍當下限。輸出的說明要寫明「背面是依輪廓推測」。
4. **背景在物件被切走的地方補平**：用周圍深度插值補洞，否則從側面看背景會有洞。
5. **輸出分開**：每個物件一個自訂形狀物件、背景一個，放在同一個群組（編輯器本來就有樹狀與群組），之後可以單獨移動、縮放、刪除。

**檢查（程式做，不靠模型說）**：每條邊剛好被兩個面共用、沒有破洞、面數不超過上限；不合格的物件退回比較粗的殼，並在結果裡標出來。這些全是純函式，可以在 node 裡單元測試。

**景物照片路徑**：UniK3D 給整個場景的公制 3D 點，物件用遮罩從中切出，各自套上面的封閉；遠景（天空、遠山）不封閉。

## 對 `image-decompose-redraw` 的影響（使用者 2026-10-29 的方向）
- 使用者的說法：**如果 UniK3D 可行**，`image-decompose-redraw` 就改成專攻「圖片轉 SVG」與「多圖層」，3D 的部分改由 `/image-to-3d` 負責。
- 現況：這個技能目前的管線是「四叉樹三角網格＋距離變換充氣成 2.5D」，3D 化是它的一個結果；`DESIGN.subject-research.md` 的 3D-3（找圖→3D）也靠它。
- **2026-10-30 進度**：3D-3 這一階已改成先呼叫 `/image-to-3d` 的同一條管線（`_i3dSubjectSolid`），舊的 2.5D 充氣只留作失敗時的退路並在結果註明；技能本身的充氣還沒拿掉，因為新舊品質並排比較沒做。
- 所以改法是**拆開**：技能只留分解（區域、圖層、SVG、前後景深排序）；2.5D 充氣那一段拿掉，3D-3 改呼叫 `/image-to-3d` 的同一條管線。拆之前必須先確認 `/image-to-3d` 的輸出品質不輸現在的充氣結果（同一批圖並排比較），否則 3D-3 會退步。
- **觸發條件要講清楚**：這個拆分以 UniK3D 實際驗證可行為前提（第一節四項驗證）。如果最後只能用 Depth Anything（階段一），`/image-to-3d` 仍然照做，但是否拿掉技能裡的充氣另外再決定，不要先拆。

## 實作現況與使用指南（2026-10-30，已實作）
**入口**：`/image-to-3d`（桌面版）、工具 `image_to_3d`、3D 編輯器裡貼圖說「把這張圖變成 3D 物件」。程式：核心 `renderer/src/media/image3d_core.js`（純函式，測試 `scripts/media-tests/image3d_core.test.js` 38 項）、主機 `renderer/src/edit/edit3d_host.js`、模型登錄 `renderer/src/vlm/vlm_core.js`。
**流程**：圖 → 深度模型（Depth Anything V2 Small；CPU 用 fp32，int8 在 CPU 跑不起來）→ 分物件（預設去背連通區；`--segment` 用 SlimSAM，實測合成圖分出 3 個；`--bg` 背景差分）→ 每個物件各自封閉 → 放進 3D 編輯器並貼原圖當材質。
**外殼**：`smooth`（預設，頂面頂點共用、無細長三角形）、`blocks`（樂高）、`cylinder`（輪廓柱體）；每一層都過封閉檢查，不合格退回較粗的殼，最後退外框方塊。**永遠不做浮雕**。
**全景／轉圈**：`--panorama`、單張寬高比 ≥2、或多張照片 EXIF 方向顯示站在原地轉圈 → 拼成橫幅、依深度切遠／中／近三層、各自封閉、彎在圓柱上、相機在圓心；繞著物體拍（inward）做不到，只用第一張並告知。
**與編輯器結合**：不認識的東西 → GitHub 找 OBJ → 找圖片 → **轉 3D**，最後一階（`_subjImage3d`）先走這條管線（`_i3dSubjectSolid`），失敗才退回舊的 2.5D 浮雕並註明。edit-game-3d 尚未接。
**驗證／限制**：測試只含核心；真實 App 的完整流程、GPU fp16、頭戴裝置 VR、新舊品質並排比較都沒驗證。單張圖看不到背面，背面是依輪廓推測。UniK3D 只有自備匯出說明，推論沒接。
