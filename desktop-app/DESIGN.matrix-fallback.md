# 設計：Blockly writer ＋ 矩陣層後備，要涵蓋哪些「可解」問題（只有設計，尚未寫產品程式）

使用者的話（2026-11-06）：「blockly-writer -> matrix-algorithms　blockly-writer評估不出來, out of scope的用matrix-algorithm評估　我們的blockly+matrix-algorithm的範式，需要可以cover所有的可解問題，讓code-writer可以產生能解決使用者需求的程式」；「上述是實現的順序的宣告，請依序完成」。

標記：【證明】＝理論標準結果；【驗證】＝我在本專案跑過程式、有測試；【推測】＝判斷，沒有實驗。
前置閱讀：`DESIGN.matrix-algorithms.md`（§5 學習、§9 小矩陣＋機器、§11 VM、§13 階層與記憶體、§14 可讀性）。

## 0. 結論（先看這裡）

1. **「涵蓋所有可解問題」不能當成可保證的承諾。** 圖靈完備的 VM 在表達力上涵蓋所有可計算函式【證明】，但「表達得出」不等於「從題目找得到」：哪個程式對應使用者的意圖，是從規格／範例推的，規格不足就推不出（Rice 定理、No Free Lunch 一類的結果；停機問題等不可判定問題本來就不可能）【證明】。產品上能說的只有：**每一級有一個保證會停的求解策略、一個誠實的「解不出」出口、以及一張實測的涵蓋表**。
2. 做法：把題目依「最少需要的記憶體」分 6 級（§2），每級配一個矩陣層元件與一個有預算（保證會停）的求解策略（§3）。
3. 後備鏈：配方 → 課 → Blockly 範式骨架 →（新）矩陣層 → 區塊迴圈（模型）。矩陣層在沒有模型時也要能走（§4）。
4. 最大缺口不是表達力，是**規格**：使用者只有敘述、沒有範例時，矩陣層沒有東西可學。必須明說、必須標 `verified:false`，不能假裝驗證過（§5）。
5. 先量再做：待辦 2 的「沒見過的 60 題」基準要在實作前跑出現況，矩陣層的每一級要用「Blockly 解不出、矩陣層能解」的題證明自己有用；沒有題證明的級就不做（§7）。

## 1. 「所有可解問題」的定義與界線

| 類別 | 能涵蓋嗎 | 理由 |
|---|---|---|
| 規格完整（敘述＋足夠範例／參考解）、可計算、輸入輸出是整數／字串／清單／格子／圖 | **原則上能表達**；找得到與否看級別與預算 | 暫存器機（計數器／堆疊／佇列／陣列）圖靈完備【證明】；搜尋有預算，預算內找不到就回報解不出 |
| 規格不完整（只有模糊敘述、沒有範例） | 不能保證 | 需求本身欠定；只能生成候選範例讓使用者確認（§5） |
| 不可判定（停機、程式等價、任意程式的性質） | 不可能 | 【證明】 |
| 複雜度上不可行（NP-hard 要精確解、n 很大） | 能寫出正確但慢的程式；不保證在時限內 | 正確性與效率分開看；基準要同時記逾時 |
| 需要外部資料／網路／畫面／裝置 | 不屬於演算法題 | 由領域包（`DESIGN.block-domains.md`）處理 |
| 輸出非確定（隨機、啟發式、需要「夠好」的解） | 只能驗性質（可行性、不劣於基準） | 判題器要換成性質檢查，這是另一件事（螞蟻、貪婪屬領域包） |

所以對外的說法是：**「在規格明確且可計算的範圍內，Blockly ＋ 矩陣層的表達力沒有缺口；實際涵蓋率以基準量到的為準，解不出的列清單」**。

## 2. 分級（沿用 §13.3 階層，加上求解需要的資訊）

| 級 | 名稱 | 最少需要 | 代表題 | 矩陣層元件（已存在） |
|---|---|---|---|---|

| L1 | 線性遞推 | 無（矩陣冪） | 費氏、爬樓梯、三項遞推取模 | Berlekamp–Massey→伴隨矩陣→`matPow` |
| L2 | 有限狀態（串→是／否／數） | 有限控制 | 二進位整除、不含連續 11、a 的個數奇偶 | Myhill–Nerode／Hankel 學 DFA／WFA；`dfaCountVM` |
| L3 | 半環圖（路徑計數、最短路、閉包、格子 DP 的視窗有界版） | 矩陣由輸入建出來 | grid 路徑數、coin-change、components、Floyd | `graphVM`、min-plus／布林閉包／計數 |
| L4 | 計數器／標量機 | ≥1～2 個無界整數暫存器 | gcd、count-primes、線性掃描二分 | VM：`iarith`、`jeq／jlt` |

## 3. 涵蓋表：等級 × 元件 × 求解方式 × 會不會停 × 要不要範例

「保證會停」＝演算法本身有明確預算上限（步數、候選數、狀態數），超過就回報解不出，不會無限搜。「要範例」＝輸入資料從哪來。

| 級 | 求解方式 | 保證會停 | 需要什麼資料 | 已驗證的程度 |
|---|---|---|---|---|
| L0 | ① 先試 `matrix_forms` 的有限秩分類；② 對固定 n 的 oblivious 題展開成比較交換網路／ReLU 編成 if | 是（維度、n 上限） | 範例或可呼叫的參考解（Hankel 要能問許多輸入） | 【驗證】`max-of-array`（秩 5）、雙調排序 n≤16；【推測】一般公式題 |
| L1 | 取題目或範例給的數列（連續 2d+2 項以上）→ BM 試 d=1..D 階 → 取模質數 → 矩陣冪→ holdout 驗證 | 是（D 上限、項數有限） | **連續數列**；2d−1 項會學錯（24/24）【驗證】 | 【驗證】費氏 F(90)；題目沒給數列時只能從敘述的遞推式讀（讀取器已有 fibonacci 課） |
| L2 | Hankel／Myhill–Nerode 合併：以範例當前綴與後綴表；狀態數上限 S（預設 12，對應 §14.5 可讀門檻） | 是（S、字串長度上限） | 要能「回答任意短字串」；範例只有 2～3 筆通常不夠【驗證：後綴長度 0 時 div3 學成 2 狀態】→ 必須由「讀取器生成短字串＋使用者／參考解標答案」補 | 【驗證】3 題（理想資料）；稀疏範例沒做 |
| L3 | **不是學，是範本**：讀取器認出輸入形狀（邊表／格子／面額），程式建矩陣，半環 4 選 1×答案格 窮舉（槽位小），沙盒驗證 | 是（槽位窮舉 ≤ 幾十種） | 範例做驗證即可；不需要大量資料 | 【驗證】`coin-change`、`grid-bfs`、`components`；其中多數已被現有範式骨架解掉（§5.5 估 17/20） |
| L4 | 枚舉合成：VM 指令集限縮在 `iarith／jeq／jlt／jmp／in／out`，程式長度 ≤ Lmax，**按長度遞增＋範例剪枝**（觀察等價：兩個程式在全部範例上輸出與軌跡相同就丟一個） | 是（Lmax、指令集有限→候選數有限；每個候選有步數上限防無窮迴圈） | 範例（越多越好）；holdout 必要 | 【推測】僅手寫 VM 的 gcd 驗證過；**枚舉合成本身沒有做過**，指數爆炸風險最大（見 §6） |
| L5 | 同 L4＋`push／pop`；骨架優先（「掃描＋堆疊配對」「逆序輸出」等有限個模板，槽位窮舉），再退到通用枚舉 | 是，但通用枚舉實務上只能到很短的程式 | 範例 | 【驗證】括號 VM 是手寫；合成沒做 |
| L6 | 骨架優先：BFS（佇列＋距離陣列）、DFS、DP 表、並查集、堆積等**模板化 VM**，槽位（鄰接怎麼建、距離怎麼更新）窮舉；通用枚舉**不承諾** | 骨架內是；通用枚舉只有預算保證 | 範例＋隱藏測資 | 【驗證】BFS／並查集／排序的手寫 VM；合成沒做 |

誠實的一句話：**L0～L3 有現成的演算法能「求」；L4～L6 現在只有「VM 能表達」與手寫範本，從範例自動合成是研究級問題，要用骨架＋有預算的枚舉，不承諾通用。**這也是為什麼 L4～L6 的實作應該是「VM 範本庫（跟 Blockly 範式骨架同構）」而不是「通用程式合成器」；後者只當最後一層小預算嘗試。

## 4. 後備鏈與接口

### 4.1 順序

`buildFromUML`：配方 → 課 → Blockly 範式骨架 →（新）**矩陣層** → 區塊迴圈（模型，需要 `pick`）。

觸發「Blockly 評估不出來」的條件（任一）：
- 讀取器沒讀出意圖（`intent` 缺）——矩陣層**也**無法用，直接進模型／失敗，不要假裝；
- 範式骨架 `forIntent` 回空；
- 範式骨架窮舉組合全未 AC（`ps.ok === false`）；
- 配方與課沒過沙盒。

### 4.2 矩陣層的輸入與輸出

輸入：`{intent, statement, examples, hidden?, budget, judge}`
- `examples`：題目 `tests`＋讀取器生成並經確認的範例（§5）；`hidden` 只供最終驗證，**不可拿去學**（HANDOFF 與 §5.3 的規則）。
- 範例先**切分**：學習集／holdout（至少留 1/3，範例少於 4 筆時 holdout 以讀取器生成的輸入對照「候選互相比對」代替，並降級標 `verified:false`）。

輸出：`{ok, source, model, cnl, matrix:{kind, level, size, tried, learned:true|false, holdout:{n, pass}}, verified}`
- `kind`：`recurrence | dfa | wfa | semiring | vm`；`level`：L0～L6；`size`：維度／狀態數／指令數；`tried`：候選數。
- 管線：求解（§3）→ **矩陣／VM 程式** → `matrix_decompile_core.js` 反編譯成 CNL → `B.parseCNL`→`toIR`→`C2U.toPython` → 沙盒（`judge`，含隱藏測資）→ AC 才算解出。

### 4.3 子順序（便宜且保證會停的先）

1. L1 遞推：只有範例／敘述帶「數列」時才試。
2. L2 有限自動機：輸入形狀是 `str`、輸出是是／否或有限值域時才試。
3. L3 半環圖：讀取器認出 `rows`／`grid`／面額＋目標時才試（多半已被範式骨架先解掉；留在這裡是給「骨架沒有、但矩陣範本有」的變體）。
4. L4～L6 VM 範本庫（骨架優先），最後才是小預算通用枚舉。
每一步的預算獨立計（候選數與毫秒），累計上限寫進 `budget`，到了就回報 `reason`，不阻塞進模型路徑。

### 4.4 反編譯到 Python 的缺口（現況）

`matrix_decompile_core.js` 現在輸出的是**中文 CNL（逐指令）**與遞推式／狀態圖／regex／if 鏈（§14.8），**沒有**「VM→區塊 CNL→Python」。要做的是：
- L1：伴隨矩陣＋`mat_pow`（範式 `matrix-power` 已有，直接套槽位）；
- L2：DFA 轉移表＋`for ch in s: state = T[state][ch]`（範式 `state-machine` 還沒有，要新增）；
- L4～L6：VM 指令→結構化區塊（`while`／`if`／`list`），限制是區塊解析器**丟掉巢狀 `def`**（HANDOFF §8 陷阱），所以遞迴題必須用 VM 堆疊展開成迴圈。
這件事（VM→結構化 CNL）是實作裡最大的工程量，先做 L1／L2／L3（直接套範式槽位，不經 VM），L4 之後再做。

## 5. 使用者只有需求、沒有測資怎麼辦（最大缺口）

事實：未知題通常只有敘述＋2～3 筆 `tests`；§5.3 已量到範例太少會學錯。方案依序，**每一種都要在回報裡標明資料來源與 `verified`**：

1. **題目自帶範例／使用者貼的範例**：直接用，切 holdout。`verified:true` 的條件＝隱藏測資（若有）或 holdout 全過且範例數 ≥ 門檻。
2. **讀取器生成輸入**（依 `intent.inputs` 的形狀隨機生成小輸入，如長度 ≤6 的串、n≤8 的清單）→ 需要「答案」：
   a. 有**參考解**（題庫的 `ref`、使用者貼的程式、舊版程式）→ 當預言機，`verified` 以預言機一致為準；
   b. 沒有參考解 → **卡片請使用者確認或補期望輸出**（問 3～5 個最有鑑別力的輸入：選能讓不同候選答案不同者，即主動學習）；使用者答了才算範例；
   c. 使用者不答 → 候選程式只能標 `verified:false`，介面明說「這是從敘述推的，沒有被任何範例驗證」，不得標已通過。
3. **候選互比**：若矩陣層與 Blockly 範式各產生不同程式，在生成輸入上比對輸出；不一致的輸入就是最有價值的提問（交給 2b）。
4. **只有敘述的題**：矩陣層**不啟動**（沒有東西可擬合）；回「需要範例」＋提供生成的輸入供填答。這不是失敗，是規格不足。【這是產品決策，要在介面落實：「待補規格」≠「解不出」】

## 6. 風險與誠實的界線

| 風險 | 說明 | 防護 |
|---|---|---|
| 範例太少→過度擬合 | §5.1 實驗：2d−1 項 24/24 學錯；後綴長度 0 的 div3 錯 12/50 | holdout、最少範例數門檻、不足就 `verified:false`；隱藏測資只做最終判定 |
| 枚舉合成指數爆炸 | VM 候選數 ~ |指令集|^長度；L4 以上通用枚舉只到十餘條 | 骨架優先、按長度遞增、觀察等價剪枝、候選數與毫秒預算、超過即放棄 |
| 解出但不可讀 | §14：VM 是人寫 Python 的 1～6 倍；稠密學出的矩陣是黑盒 | 狀態上限 S（預設 12）、必須反編譯得出才收（§14.7 第 6 條）、狀態命名 |
| 合成的程式只對範例成立 | 通過範例≠對意圖 | 沙盒隱藏測資、隨機輸入對照參考解（有參考時）、holdout |
| 巢狀 def 限制 | 區塊解析器丟掉巢狀 `def` | 遞迴題走 VM 堆疊→迴圈，或先修限制 |
| 效能 | 矩陣冪 O(r³ log n)；one-hot 記憶體每次 O(n) | 輸出的程式要加時限測資（基準記逾時） |
| 「涵蓋」被誤讀成全部 | 使用者可能以為零失敗 | 介面與文件只報基準數字與解不出清單 |

## 7. 實作順序與檢核（待辦 2～4 的契約）

1. **待辦 2 基準先行**：≥60 題、分 L0～L6＋其他，每題有 `statement／tests／hidden／ref`，刻意是種子沒見過的；跑三種模式（只 Blockly／＋矩陣層／＋模型，沒模型跳過）。輸出每級題數、解出數、用到哪層、嘗試次數、耗時、**解不出清單與原因**（含「規格不足」「逾時」「合成預算用盡」「骨架缺」）。現況基準在矩陣層實作**之前**先跑，作為「沒有矩陣層」的對照。
2. **待辦 3 逐級做**，順序按 CP 值：L1（遞推，套 `matrix-power` 槽位）→ L2（新增 `state-machine` 範式＋Hankel 學習）→ L3（半環範本）→ L4/L5/L6 VM 範本。**一級的進場條件**＝基準裡有「Blockly 解不出、這級能解」的題；沒有就不做這級。每級附：隨機輸入對照參考解、holdout、沙盒、過度擬合的反例測試（故意給太少範例，必須回報 `verified:false` 或不產生程式）。
3. **待辦 4 宿主接線**：`_codeOffline` 走新鏈；結果顯示用了哪一層；`offline-code.eval.js` 擴充；真 Electron 評估。
4. 驗收：每個承諾的數字來自基準；解不出的題在 `STATUS.md` 列清單；不得出現「涵蓋所有問題」字樣。

## 8. 待改善（現在就知道的）

- 範式骨架庫與矩陣範本有大量重疊（§5.5：現有骨架已解 17/20）；矩陣層的邊際價值要靠「沒見過的題」基準證明，現在沒有數字，**這份設計的有效性是【推測】**，要等待辦 2。
- L4～L6 的通用合成沒有任何實驗；本文把它定位成「最後一層、小預算、不承諾」。
- VM→結構化 CNL→Python 的反編譯沒有；L1～L3 可以繞過 VM，直接套範式槽位。
- 讀取器對「沒有範例」的題的生成輸入與主動提問（§5）需要新的卡片介面，未設計 UI。
- 範例切分（holdout）在範例 ≤3 筆時統計上很弱；只能降級標示，不能靠它宣稱正確。

## 11. 矩陣 → UML／Blockly（支援 code edit）（使用者 2026-11-06 新增方向，只有設計，排在矩陣層有進步之後）

使用者原話：「我們有matrix的decompiler，可以從這變成matrix -> uml/blockly來支援code edit吧」。

### 11.1 現況（我讀過的）
- `renderer/src/algo/matrix_decompile_core.js` 目前輸出：狀態圖文字／Graphviz dot、正規表示式、遞推式、if／else 原始碼、逐指令的中文 CNL（§14.2）。**沒有 UML，也沒有 Blockly 區塊。**【驗證：讀過檔案與 §14】
- 既有的 code edit 路徑：Python → tree-sitter → `py_code2uml_core.js`／`py_blocks_core.js`（程式 → UML／區塊），區塊 → `toIR` → `toPython`（區塊 → 程式）。這條路徑**從程式碼出發**。矩陣層的產物是 Python 程式（§4.2），所以「合成出來的程式」本來就能走這條既有路徑進區塊編輯器。

### 11.2 兩條路是否合流
結論（設計）：**合流在 Python 這一層，不開第二套編輯模型。**
- 路 A（既有）：Python 原始碼 → tree-sitter → 區塊／UML。
- 路 B（新）：矩陣／VM／ReLU 樹 → 反編譯 → 區塊／UML **直接產生**（不經 Python 文字）。
- 差別只在「來源是否已知結構」：路 B 知道每個格子的意義（狀態名、暫存器名），產生的區塊可以帶**有意義的名稱與註解**；路 A 從任意程式碼還原，只能靠命名猜。兩者輸出同一種中間表示（區塊 IR），之後的編輯、`toPython`、沙盒完全共用。
- 因此路 B 只是「更高品質的區塊來源」，不是另一個編輯器；失敗時（反編譯不出）退回路 A（Python → 區塊）。

### 11.3 對應表（要做的反編譯目標）
| 矩陣層元件 | → UML | → Blockly（區塊 IR） | 現有基礎 |
|---|---|---|---|
| DFA／one-hot 轉移矩陣 | 狀態機圖（狀態、轉移、接受集） | 轉移表＋`for ch in s: q = T[q][ch]`（目前範式 `state-machine` 還沒有，要新增） | `dfaToText／dfaToDot` |
| 遞推（伴隨矩陣） | 一個操作 `f(n)`＋註解寫遞推式 | `mat_pow` 區塊（`DESIGN.ast-nodes.md` 7.2）＋初始向量／係數槽位 | 遞推式反編譯、範式 `matrix-power` |
| ReLU 決策樹 | 條件分支（活動圖） | `if／else` 區塊 | ReLU→if 反編譯 |
| VM 程式 | 活動圖（指令＝動作、跳轉＝分支） | 區塊序列：`while`／`if`／清單操作（受巢狀 `def` 限制，見 HANDOFF §8） | VM→中文 CNL（逐指令） |

### 11.4 編輯迴圈與往返（round trip）
1. 使用者在 UML／區塊上改（例如改狀態轉移、改遞推係數、改 if 條件）。
2. 重新編譯：區塊 → Python（既有 `toPython`）；若來源是矩陣型，同時**重建矩陣**（改的是表／係數就直接更新矩陣，不用重新合成）。
3. 沙盒重驗（範例＋隱藏測資）；沒過就把判決回給使用者，不靜默覆蓋。
4. **往返要求**：矩陣 → 區塊 → 矩陣，得到的矩陣與原矩陣在隨機輸入上輸出相同（測試條件，同 §14.7 第 3 條）。只能單向的（反編譯不出的稠密矩陣）不進編輯器，只當候選。
- 限制：使用者改出矩陣型不能表示的邏輯（例如在 DFA 裡加入計數）→ 退出矩陣模式，改成一般 Python 區塊（降級而不是拒絕）。
