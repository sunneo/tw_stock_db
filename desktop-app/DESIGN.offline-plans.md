# 離線多步驟計畫（Plan）：目標 → phase → step → substep，用狀態機與決策樹維護

> 接在 `DESIGN.offline-recipes.md`（單一工具食譜）之後：當使用者的目標需要好幾個工具接力（影片做摘要、網頁摘要、上網查資料並整理、文件摘要後念出來…），離線小模型不自己「想」計畫，而是由程式規劃、狀態機執行、決策樹維護。
> 核心 `renderer/src/recipe/plan_core.js`（`FaPlan`，純函式 UMD，測試 `plan_core.test.js` 55 項）；宿主端 `floating-assistant.js` 的 `_planAnswer`／`_planRun`／`_planResume`。

## 1. 為什麼不叫模型規劃
0.6B 的模型寫不出可靠的多步驟計畫（會漏步驟、編工具名、順序錯、資料接錯）。所以：**規劃是程式的事，模型只在兩處出手**——目標有歧義時從選單挑一個、程式填不出的欄位補空（沿用食譜的 `modelFill`：數字必須是使用者說過的、不知道填 null）。

## 2. 從目標到計畫

```
使用者的話 ─► ① 目標分類 ─► ② 規劃（倒推）─► ③ 展開（phase／step／substep）─► ④ 執行與維護（狀態機＋決策樹）─► ⑤ 成果與學回去
```

### ① 目標分類（決策樹第一層，程式）
`GOALS` 是一張資料表：目標、要什麼成品（`target` 種類）、手上要有什麼（`needs`：影片／音檔／網址／查詢／文件／PDF…）、觸發字。`matchGoals(text, facts)` 用「觸發字＋手上有的東西」過濾（有影音附件時「摘要」是影片摘要不是文件摘要；有網址時網頁優先；更特定的目標贏過一般的），**剛好一個就程式決定**；兩個以上都合理才讓模型從編號選單挑（可選 0＝都不是）；沒有就不走計畫（交給單一工具食譜）。

手上有的東西（`facts`）：附件（依副檔名分類）、這句話裡的網址、查詢字串、使用者的話。**對話裡更早附的檔案只有使用者用「這份／上面那個／剛剛」指它時才算**；規劃只從目標「要的輸入」出發（`goal.needs`），不會因為對話裡剛好有別的文字檔就跳過抓網頁（實測抓到的 bug，見 §6）。

### ② 規劃（程式，倒推）
`CAPS` 是有型別的工具能力表：每個工具吃什麼種類（`in`，可 `many`、`min`、`optional`）、產出什麼種類（`out`：種類＋回傳 JSON 裡放 file_id 的鍵或 inline 文字）、階段（取得／準備／分析／產出）、成本、是否需要線上模型、是否很慢、是否是宿主程式（`local`）。

`buildPlan(goal, facts)`：目標要什麼種類的成品 → 手上沒有就找能產出它的工具 → 它的每個輸入再遞迴找 → 到手上有的東西為止，**取成本最低的一條路**（深度上限 5、有循環保護、同一步驟去重）。成本：需要線上模型但現在離線 +50（所以離線時自動走離線摘要）、很慢 +0.5。資料怎麼接由種類決定——上一步的成品餵給下一步的哪個欄位**不問模型**。呼叫端可以覆寫輸入種類（例如「摘要後念出來」：語音的文字來源只能是摘要，不能直接念整份文件）。

範例（離線）：
| 手上有 | 目標 | 計畫 |
|---|---|---|
| 影片 | 摘要 | `transcribe_media` → `local_summarize` |
| 網址 | 摘要 | `fetch_web_page` → `local_summarize` |
| 一句查詢 | 摘要 | `browser_search` → `pick_urls` → `fetch_web_page` → `local_summarize` |
| docx／PDF | 摘要後念出來 | `parse_uploaded_file` → `local_summarize` → `text_to_speech` |
| 影片＋（離線沒有字幕）| 字幕燒進影片 | `burn_subtitles`（自己內部先轉逐字稿） |

### ③ 展開成 phase → step → substep
路徑依階段分成 phase（取得資料 → 準備素材 → 分析處理 → 產出成品，只列用到的），每個 step 再拆成 4 個 substep：**綁定輸入 → 呼叫工具 → 驗證成品 → 登記成品**。計畫以文字卡片呈現（☐ 待做、▶ 進行中、✅ 完成、❌ 失敗、⏭️ 略過、🔁 被換路取代、⏸️ 等你補資料），執行中即時更新進度卡片。有「很慢」的步驟（轉逐字稿、燒字幕）執行前先問一次。

## 3. 狀態機與決策樹（`advance`）
- **步驟狀態**：pending → running → done／failed／skipped／replaced／waiting。**計畫狀態**：ready → running → waiting／done／failed。
- **綁定輸入**（程式）：依種類從「手上有的」與「前面步驟的成品」找；`many` 欄位收齊同種類全部、不夠就缺。工具自己的其他必填欄位（例如 `pages`）：程式先填（`programFill`）→ 模型補空 → 還缺就**問使用者**（計畫停在 waiting，保存狀態；下一句話就是答案，補進去從停下的那一步接著做，**已完成的不重做**）。
- **驗證成品**：工具回報成功但沒有宣告的成品（例如沒有 `pdf_file_id`）→ 當成失敗，不會把「看起來成功」往下傳。
- **失敗時的決策樹**（`FAILURE_RULES`，資料化、可檢視、每次決策都記錄）：選填步驟 → **略過**；暫時性錯誤（逾時、連線、429/503）且重試少於 2 次 → **重試**；缺東西（沒有附件、找不到檔案、密碼保護）→ **問使用者**；工具做不了這個輸入（不支援格式、沒有模型、離線）→ **重新規劃**：把壞掉的工具排除、已經產出的成品當作新的 facts 重新倒推一條路（已抓好的網頁不會重抓）；其他 → 重新規劃；沒有別條路 → **中止，並交出已完成的步驟與成品**，不編造。
- **一定收斂**：呼叫上限 14、重新規劃上限 2、每個 step 重試上限；上限到了就中止，錯誤寫進狀態。
- **決策記錄**：目標怎麼選的（程式／模型）、計畫的步驟、每個決策（規則、動作、原因）、結束狀態，進 `fa_recipe_traces_v1`（設定頁可匯出）。

## 4. 離線摘要（`local_summarize`）
`summarize_large_text` 需要線上模型；離線時由程式＋離線文字模型做：依**模型上下文長度自適應切段**（`FaVlm.textBudget`，不寫死）→ 每段讓模型列 2～4 個重點，之後被 `checkExtractive` 檢查（沒有來源沒有的數字、詞彙大致都在來源裡）→ 沒過的那一段改用程式的**抽取式摘要**（`extractiveSummary`：句子切分、詞頻加權、開頭加分、保留原順序）；太長（>4 段）先用程式挑 40 個重點句再讓模型摘要；沒有模型就全部用程式摘要。結果標明方法（model／extractive／mixed）。

## 5. 線上 AI 養大離線 AI；離線模型最大化使用離線訓練器
離線訓練器是橋：**線上 AI 的做法、RAG、使用者教的，都存在訓練器裡，離線模型每一步都去用它。**

| 訓練器裡的東西 | 怎麼被離線模型用 |
|---|---|
| 規則、語意範例（線上對話學到的工具＋參數樣板、使用者教的） | 候選工具的來源；**訓練器已替選定的工具填好的欄位優先**（標示「訓練器」，模型要補的越少）；分數差距夠大程式直接路由 |
| 學到的做法（`steps` 多步驟樣板、已學會的解法快取） | 同一句話再來，訓練器直接重放（不進模型）；信心不足時當參考資料 |
| 相似問法、過去問答（含線上對話與 RAG 學來的） | 整理成**參考資料包**（`buildReferencePack`）給離線文字模型：依種類排優先（做法 > 規則 > 相似問法 > 過去問答 > RAG）、標出處、**過去問答標年齡並註明可能過期**、整體份量依模型上下文按比例給 |
| RAG | 同上，進參考資料包 |
| 訓練器的 slot 抽取（網址、路徑、引號、數字） | 食譜與計畫的 `facts`／欄位來源 |

**離線做成功的，也養回訓練器**（`_recipeLearnBack`，照「自動訓練」設定，`off` 不學）：成功的食譜／計畫把「這句話 → 工具＋參數」學進訓練器，下次同樣的話訓練器自己就能處理，不再進食譜與模型。實測：「幫我把這張圖轉成pdf」＋附件做成功後，訓練器多了學到的 `images_to_pdf` 樣板與一筆解法快取，下一次同一句直接命中快取。

**修掉的養成污染**：學到的參數樣板裡會帶著那一次的**檔案 id**（uuid），以後每次都會去轉上一次的圖。現在樣板裡的 uuid 欄位整個移除（`_otStripFileIds`，線上 AI 的自動學習也一起修了），檔案由食譜從那一次的附件補。

**養成的入口就是離線訓練器本身**（Configure → AI →「離線訓練器」：自動訓練模式、整理成技能、用 RAG／對話訓練、乾跑與規則編輯都在那裡）——離線訓練器原本的用途就是被線上 AI 養大。「離線模型管理」頁只留一行指向它，不另外做一套；離線訓練器頁加了一段說明離線模型怎麼使用它養出來的東西。

## 6. 實測（打包版 Electron、CPU 4 執行緒、Qwen3 0.6B；訓練器門檻 1.0，所有句子進食譜）
- **文件摘要**（上傳的 txt）：目標由程式決定 → `local_summarize`（分段摘要，模型寫、被檢查）→ 40 秒。
- **網頁摘要**（example.com）：`fetch_web_page` → `local_summarize` 兩步完成，約 24 秒。
- **上網查資料並整理**：「上網查 rust borrow checker 並整理重點」→ `browser_search` → `pick_urls` → `fetch_web_page` → `local_summarize` **4 步全部完成**（真的上網）；摘要段落有模型寫的重點，也有被檢查擋下後改用程式抽取的句子；整個約 6.5 分鐘（長網頁要分 4 段、CPU 上每段幾十秒）。
- 整個過程主執行緒最大延遲 99 毫秒、超過 100 毫秒的次數 0。
- 學回去：見 §5。
- 單元測試：`plan_core.test.js` 55 項（目標分類、倒推規劃、展開、狀態機、重試、換路重新規劃、略過、問使用者與繼續、上限、成品驗證、成品登記）、`recipe_core.test.js` 69 項（含參考資料包、抽取式摘要、切段）。

抓到並修掉的 bug：
- 規劃把對話裡舊的文字檔當成網頁摘要的輸入，跳過抓網頁 → 規劃只從目標要的輸入出發；舊附件要使用者指到才算。
- 「上網查…並整理重點」被文件摘要搶走（觸發字距離上限太小；舊附件）→ 距離放寬、特定目標優先。
- 搜尋字串帶著「並整理重點」→ `cleanQuery` 去掉尾巴。
- 同一份計畫被執行兩次時狀態互相污染 → 建立執行時深拷貝。
- 重新規劃成功後原本失敗的步驟讓整體顯示失敗 → 新增 `replaced` 狀態。
- 學到的樣板帶檔案 id → 見 §5。

## 7. 限制（誠實）
- **影音那條路（`transcribe_media`、`burn_subtitles`、`extract_audio` 等）只用假工具測過狀態機與規劃，沒有拿真影片端到端跑**（沒有測試影片，Whisper 也要下載）；它們的回傳成品鍵是依工具說明與 `*_file_id` 慣例猜的，登記時還會掃描任何 `*_file_id`，第一次真實使用請看計畫卡片與決策記錄。
- 能力表是人工維護的（約 15 個工具）；新增工具要補一筆 `CAPS`（吃什麼種類、產出什麼種類），否則計畫看不到它。
- 上網查資料只抓第一個網址，不是多網頁彙整。
- 離線摘要在 CPU 上很慢（每段幾十秒），模型寫的段落常因檢查被改用程式摘要；品質是「重點句擷取」等級，不是流暢改寫。
- 0.6B 常輸出簡體字。
- GPU 路徑沒在這台機器實測。
- 離線訓練器預設「自動訓練」是 off——養回去要使用者開。

## 8. 移植到 宿主專案
帶走 `plan_core.js`＋`recipe_core.js`＋測試。宿主要提供：工具表與 schema、`env.tool`／`env.fns`（本機函式）、`env.fill`（模型補空）、`env.save`、附件與訓練器的 facts，以及 CAPS 裡對應自己工具的條目（宿主專案 的 TestLink、Gerrit、wiki 等工具各補一筆種類簽章即可，規劃與狀態機不用改）。
