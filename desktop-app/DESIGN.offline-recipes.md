# 離線小模型的「食譜」（Recipe）：讓 0.5～1.7B 的離線模型也能做工具型的服務

> 對象：要讓離線文字模型（`DESIGN.offline-text.md`）完成現有服務（圖片轉 PDF、查錯誤碼、搜尋、抓網頁、影音處理…）的人。
> 概念來自 宿主專案 那邊的 recipe 設計指南（決策樹＋狀態機＋選擇題／填空題、typed function calls、決策記錄）。
> 核心在 `renderer/src/recipe/recipe_core.js`（`FaRecipe`，純函式 UMD，測試 `recipe_core.test.js` 58 項），宿主端在 `floating-assistant.js` 的 `_recipeAnswer`。

## 1. 為什麼

0.6B 的模型做不到自由的 tool loop：基準測試只有 5/6（還要簡短提示詞才穩）、Qwen2.5 0.5B 只有 1/6；寫回答時會編造、重複、被糾正後複誦同一個錯誤。所以工具型的服務**不給它自由文字、不給它整個工具清單**，而是：

| 誰 | 負責 |
|---|---|
| **程式** | 擁有狀態與選項；凡是能程式決定的就程式決定——路由（證據、分數差距）、欄位（網址、路徑、附件、引號、列舉、預設值）、驗證、執行、結果整理 |
| **模型** | 只看到「現在是第幾步、這一步要什麼」，**沒有前面步驟的記憶**；只做剩下的：從編號選單挑一個、填型別固定的欄位、用 1～2 句話說明（之後被檢查） |
| **驗證器** | 每個模型回覆都被檢查；不合格就退回（模型只看到「它自己最後一次的回覆＋精確的錯誤」，不累積歷史，最多 2 次，連續兩次完全相同就提前停止） |
| **決策記錄** | 每個決定都記下來：誰決定的（程式／模型）、選項、被退回的原因 |

設計判斷標準：**如果一個決定可以用程式做，就不要問模型。** 真機測試發現模型做錯，解法是把該決定搬回程式，不是調提示詞。

## 2. 流程（`_recipeAnswer`）

```
離線訓練器：planned ─────────────► 照原本的路執行（不經過食譜）
          needs_input（只缺參數）──► 食譜：補欄位（forceTool = 訓練器選定的工具）
          unresolved（信心不足）──► 食譜：路由 → 欄位 → 執行 → 措辭
                                      │ 沒有合適的工具（模型選 0）／選不出來
                                      ▼
                                   離線文字模型：單純文字生成（食譜開著時不跑自由工具迴圈）
```

食譜開關：設定頁「離線模型管理」→「食譜模式」（`offlineRecipes`，預設開）。沒有 slash command：離線文字模型與食譜只有兩種進入方式——離線訓練器信心不足，以及線上模型全部失敗／斷線的自動備援（備援時不問使用者、不偷偷下載）。

### ① 路由
候選工具＝離線訓練器的最佳比對與替代方案（有工具的）＋三個唯讀常用工具（`ref_lookup`、`browser_search`、`fetch_web_page`），最多 6 個，各自帶 JSON Schema。

1. **用證據縮小候選**（`narrowByEvidence`，程式）：文字裡有網址 → 只留有 `url` 欄位的工具；有附件 → 只留「必填的檔案欄位能用這些附件（依副檔名分類）填滿」的工具。縮到只剩一個就程式決定。
2. **分數差距**（`autoPick`，程式）：第一名 ≥ 0.5 且領先第二名 ≥ 0.12 → 程式決定。
3. 否則**模型從編號選單挑**（`chooseTool`）：`{"choice": N}`，0＝「都不是（一般聊天或問答）」；選單不放工具參數、不放範例。

### ② 欄位（`programFill` → `modelFill`）
欄位定義直接從工具的 JSON Schema 來（`slotsFromSchema`），所以**現有的每一個工具都自動成為一份食譜**，不用逐一手寫。

- **程式先填**：列舉值（文字裡剛好出現一個，單字母的不比對、網址先拿掉）、網址、路徑、附件（依欄位名稱與描述判斷種類：圖片／PDF／影片／音訊／字幕）、搜尋／問題類欄位（`cleanQuery`：去掉網址、「上網搜尋／幫我查」這類指令動詞、「是什麼」這類尾巴；引號內容與冒號後面優先）、單一必填數字欄位＋文字裡剛好一個數字、schema 的預設值。
- **模型補空**：只問「必填但程式填不出來」的欄位。強制 JSON；提示詞不放範例值；**不知道就填 null，不准編**；驗證器擋下不認得的欄位、列舉值不在清單、型別不對、超出範圍、**數字不是使用者話裡出現過的數字**。模型填 null 或仍填不出 → 不執行，直接告訴使用者還缺什麼（不亂猜）。
- **選填欄位**：只有「使用者的話跟欄位名稱或描述有關」（`relevantOptional`）才問模型，沒有關連就不問、讓工具用自己的預設——避免模型為了填空而編。刻意保守：「前 5 秒」不會被猜成 fps／寬度。

### ③ 執行
有副作用的工具（`FA_OT_RISKY_TOOL`）先問使用者。成功／失敗都用 `_otPretty` 整理給人看。

### ④ 措辭（只對資訊類結果：search／fetch／lookup／query／read／parse／summar／ask／explain）
模型用 1～2 句話說明工具結果，之後被 **extractive 檢查**（`checkExtractive`）：數字與英文識別字必須（幾乎）全部出現在來源裡、**不能有來源沒有的數字**，中文詞用較寬的門檻（0.6）；過不了就丟掉、用程式整理的結果。這一步在實測裡常被擋下（例如模型在說明 errno 2 時加了來源沒有的東西），這是設計上的安全閥，不是 bug。

### ⑤ 決策記錄
`{stage, tool/options, answer, by:'program'|'model', tries, rejected[]}`，存 localStorage（最後 30 筆、400KB 上限，`pushRing`），設定頁「匯出決策記錄」輸出 JSON lines、「清除」刪掉。範例：`narrow:program:fetch_web_page → route:program:fetch_web_page → slots:program:url → run:program:ok → phrase:model:rejected`。

> **多步驟計畫（目標 → phase → step → substep，狀態機＋決策樹）已實作，見 `DESIGN.offline-plans.md`**；線上 AI 養大離線 AI、離線模型最大化使用離線訓練器也寫在那份。

## 3. 多步驟食譜引擎（`runRecipe`）
宿主專案 那種「宣告式步驟」的引擎也移植了：`steps` 有 `tool`／`compute`／`phrase`／`render`，`{{slots.x}}`、`{{vars.<步驟>.欄位}}` 內插，整串剛好是一個參照就保留原值；`optional` 步驟失敗只是略過；`compute` 只能呼叫註冊的具名函式（**不從食譜檔帶程式碼**）；`MAX_STEPS = 12`；`validateRecipe` 檢查 id、重複、未知類型、`result` 指向。**目前還沒有登記任何內建的多步驟食譜**——現有服務靠「每個工具自動成為單步食譜」；要做「轉逐字稿→摘要」這類流程，照這份格式加宣告即可（測試過引擎本身）。

## 4. 實測（打包版 Electron、CPU 4 執行緒、Qwen3 0.6B；訓練器門檻拉到 1.0，所有句子都進食譜）

| 說的話 | 路由 | 欄位 | 結果 | 模型呼叫 |
|---|---|---|---|---|
| 「幫我把這張圖轉成 A4 的 pdf」＋圖片附件 | 程式（證據：有附件） | `files`＝附件（程式）、`page_size`＝a4（程式） | PDF 產生（78KB） | **0 次，0.3 秒** |
| 「幫我看一下這個網頁 https://example.com 在講什麼」 | 程式（證據：有網址；`git_clone` 也有 url 欄位，但分數與有網址的 `fetch_web_page` 比後者勝出——證據只縮小，仍有 2 個時看分數） | `url`（程式） | 抓到頁面預覽；措辭被檢查擋下，用程式結果 | 1 次（措辭，被擋） |
| 「請查一下 errno 2 是什麼意思」 | 程式（分數差距） | `query`（程式） | `lookup_error_code` 查到 ENOENT | 1 次（措辭，被擋） |
| 「上網搜尋 rust borrow checker 是什麼」 | 程式 | `query`＝`rust borrow checker`（程式清理） | `browser_search` | 0 次 |
| 「你好，今天天氣真好」「今天心情不好，聊聊」 | 模型從選單選 0（都不是） | — | 交給文字生成 | 路由 1 次＋生成 |
| 「把影片的前 5 秒轉成 gif」（沒附影片） | 模型選 `convert_to_animated_gif` | 沒有欄位被亂填 | 工具回報讀不了檔案（沒附影片） | 路由 1 次 |

- 主執行緒：整個過程最大延遲 88 毫秒、超過 100 毫秒的次數 0。
- 對照：同一個模型走自由工具迴圈，只有「句子裡明講工具名稱」才會呼叫；走食譜，大部分句子連模型都不用問。

## 5. 修過的坑（都在測試裡有案例）
- 一開始選填欄位無差別問模型 → 模型為了填空填了 `fps`、`max_width`（編的）→ 改成「只有跟欄位名稱／描述有關才問」＋「數字必須是使用者說過的」。
- `after_colon` 把網址裡的 `https:` 當成冒號 → 查詢字串變成 `//example.com 在講什麼` → 改用 `cleanQuery`（先拿掉網址）。
- 單一字母的列舉值（`a`）被網址裡的 `/a` 誤中 → 列舉比對要求 ≥2 字元，且先拿掉網址。
- 「合併成一份 PDF」被語意功能卡搶走 → 規則信心與離線訓練器種子版本（見圖片轉 PDF）。
- extractive 檢查最初用「連續中文字的二字詞」會把動詞改寫全判為編造 → 英文／數字嚴格、中文較寬。

## 6. 限制（誠實）
- 小模型不會因為「前 5 秒」這種鬆散說法自己決定哪個欄位（start／end／duration）——要說「結束秒數 5」這種跟欄位描述對得上的話，否則不填、用工具預設。
- 路由選單只有 ≤6 個候選；訓練器沒有候選時只有三個常用唯讀工具。模型選 0 會交給文字生成（答案可能編造，沒有 RAG 或工具結果時尤其）。
- 措辭常被檢查擋下 → 使用者看到的是程式整理的結果（較生硬但不會錯）。
- 多步驟食譜目前只有引擎，沒有內建宣告。
- GPU 路徑沒在這台機器實測（顯示卡沒有 `shader-f16`）。

## 7. 移植到 宿主專案（或其他宿主）
帶走 `recipe_core.js`＋測試（純函式，只依賴注入的 `generate`／工具呼叫）。宿主要提供：工具表與 JSON Schema（`parametersSchema`）、附件清單（id＋檔名）、離線訓練器抽出的欄位（網址、路徑、引號、數字）、一個能強制 JSON 的文字生成函式（本專案是 `_llmGenerate`）、危險工具的確認介面。宿主專案 現有的 `fillSlots`／`recipePhrase`／`jsonStep` 對應到這裡的 `modelFill`／`phraseMessages＋checkExtractive`／`jsonStep`，行為一致（退回只帶最後一次回覆與精確錯誤、相同回覆提前停止）。
