# 離線訓練器路線圖：隨使用成長，最終能離線生成文字與推理

> 2026-10-04（同日修訂：文字生成與思考鏈是**通用能力**，不是專用於建置系統或錯誤解析）。
> 目標（使用者的方向）：離線訓練器**隨著使用而成長**；除了 pattern 規則（DSL），也要能看懂各種輸入（gdb、Linux journal、核心日誌、kernel panic…）；**最終**要能在離線狀態下做**一般用途的文字生成與思考鏈**——任何領域、任何任務都能用，錯誤診斷只是其中一個領域。
> 這份文件說明「現在做到哪、整體架構、下一步」。**第 3 階段以後是規劃，還沒有實作**，不要當成已完成的功能。
> 相關：`DESIGN.reference-knowledge.md`（知識與日誌診斷的實作）、`DESIGN.offline-trainer.md`（離線訓練器本體）。

## 1. 先釐清：三種不同的東西

| 層 | 是什麼 | 通用嗎 | 現況 |
|---|---|---|---|
| **領域知識** | 某個領域的規則與事實：錯誤碼、命令選項、日誌診斷規則、API 語意、某產品的操作流程… | 各領域各自一份（資料） | 已有：錯誤碼、命令、pragma、API 語意、日誌診斷（約 200 條）、離線工具與狀態機 |
| **生成能力**（文字生成） | 把「要說的事實」組成一段通順、結構合理的文字：回答、摘要、說明、報告、郵件草稿、步驟說明 | **通用**：與領域無關，領域只提供事實與詞彙 | 只有雛形：模板拼接（規則的 `what` 加槽位、診斷的 `summary`） |
| **推理能力**（思考鏈） | 從已知事實與目標，一步一步推到結論或計畫：判斷、比較、排除、規劃、決定下一步 | **通用**：與領域無關，領域只提供事實與規則 | 只有雛形：狀態機執行器、步驟（steps）、診斷的傳遞鏈 |

**設計原則**：生成與推理的引擎**不得知道任何領域**。領域知識以資料（事實、規則、模板、詞彙）注入；診斷、報告撰寫、問答、任務規劃都是「同一個引擎＋不同資料」。如果某段程式碼裡出現 `make`、`bitbake`、`errno` 這種字，它就不屬於通用引擎，要放進領域資料。

## 2. 成長的迴圈（已實作的骨架，也是通用的）

```
輸入（問題／日誌／任務）──► 離線處理（規則、語意比對、領域工具）──┬─► 成功：回答
                                                               └─► 做不到的部分 ──► 待學習清單（已實作於日誌診斷；通用化是下一步）
待學習清單 ──► AI（擴充領域）找資料或示範 ──► 以「可驗證」的形式寫入（規則＋範例＋來源）
執行期知識 ──► 匯出 ──► 人／Claude 覆核 ──► 升級成內建
```

原則：
1. **每一筆成長都可驗證**：規則附範例、知識附來源、模板附測試輸入輸出；壞的進不來。
2. **不確定就說不確定**：離線沒有把握時承認，並說明缺什麼，而不是編。
3. **越常見越先補**：待學習清單依出現次數排序。
4. **知識與引擎分離**：成長的是資料（DSL、JSON、模板），不是程式碼。

## 3. 現況（第 1 到 2 階段，已實作）

| 能力 | 狀態 |
|---|---|
| 規則、語意比對、離線工具、狀態機、步驟、JS 工具（離線訓練器本體） | 已有（`DESIGN.offline-trainer.md`） |
| 領域知識：錯誤碼、命令與手冊、pragma、API 語意 | 已完成（`DESIGN.reference-knowledge.md`） |
| 領域知識：日誌診斷（建置、gdb、核心日誌、panic、journal，約 200 條規則，輸出根本原因、連帶結果、傳遞路徑） | 已完成；這是「領域知識」，**不是**通用推理引擎 |
| 待學習清單、規則範例驗證、匯出、升級成內建 | 已完成（目前只接日誌診斷） |

限制（誠實說明）：診斷規則以逐行正規表示式為主，另有「多行規則」（`start:`＋`span:`）只收少數幾種格式（Python Traceback、核心 Call Trace、CMake 多行區塊、gcc 包含鏈）；目前的「生成」只是模板拼接，「推理」只是規則命中後的人工整理順序，兩者都還不是通用能力。

## 4. 第 3 階段：通用的離線文字生成（規劃，未實作）

目標：任何領域的事實都能被組成可用的文字，且**不靠大型模型**，先用規則、模板與規劃。

### 4.1 架構（三層，領域無關）

1. **事實層（輸入）**：領域模組把「要說的事」交成統一的結構——一組帶型別的事實：`{主體, 關係, 內容, 證據, 重要性, 確定度}`。診斷輸出、查詢結果、RAG 片段、使用者資料、工具結果都轉成同一種事實。
2. **文件規劃層（說什麼、先後次序）**：決定結構與取捨——開頭句、要點排序（依重要性與依賴關係）、合併重複、省略不重要的、在需要時插入警告或前提、決定詳細程度。規劃用**修辭結構模板**（例如：結論→依據→做法→風險；問題→原因→對策；摘要→細節；比較表）。模板是資料，不同文體（說明、報告、郵件、步驟、問答）各一套。
3. **語句實現層（怎麼說）**：把規劃好的單位轉成句子——模板加槽位（現有的 `{名稱}` 機制）、詞彙與語氣表（可由領域或使用者提供）、句型變化、中英文雙語、簡繁用語、單位與數字格式；連接詞與指代由實現層處理（「它」「這個」「另外」）。

### 4.2 品質保證

- **事實一致性檢查**：輸出文字中的每個專有名詞、數字、檔名、引用，必須能回溯到輸入事實；回溯不到就不輸出該句（寧缺勿濫）。
- **可重現**：同樣的事實與設定產生同樣的文字（不靠隨機）；需要變化時用明確的種子。
- **可測試**：每個模板與規劃規則附「輸入事實 → 預期輸出」的測試，像規則附範例一樣；成長時一併驗證。

### 4.3 成長方式

- 使用者或 AI 示範一段好的輸出 → 系統嘗試從中**抽出模板**（把具體值換成槽位）並提示確認 → 存為資料，附原始範例當測試。
- 使用者修改了生成的文字 → 記錄差異，累積成「偏好」（用語、長度、語氣、固定開頭結尾）。
- 領域知識增加時，生成自動受益（因為領域只提供事實與詞彙）。

## 5. 第 4 階段：通用的離線推理鏈（規劃，未實作）

目標：不只給結論，而是能展示「怎麼推到這個結論」，並在資訊不足時知道**下一步該做什麼**——**對任何領域都適用**（診斷、選擇、比較、規劃、排程、問答）。

### 5.1 架構（領域無關）

1. **知識表示**：事實（有確定度與來源）＋規則（若 條件 則 結論，附確定度與適用範圍）＋目標（要回答的問題或要達成的狀態）。領域用資料提供這些；診斷規則的 `cause:`／`fix:` 就是其中一種資料。
2. **推理引擎**：
   - **前向推理**：從已知事實套規則，得到新事實，直到沒有新結論。
   - **假設推理**：對一個現象列出候選解釋，依證據加權、排除與矛盾的，保留分數最高者；分數接近時**不選邊**，列出平手項與能區分它們的檢查。
   - **規劃**：目標分解成子目標與步驟（可重用現有狀態機 `_faOtFsmRun` 與 steps），每步有前提與預期結果，失敗時回到上一個分支。
   - **資訊需求**：推理到卡住時，產生「還需要知道什麼」（缺哪個事實），離線也能向使用者追問，使用者回答後繼續。
3. **推理鏈的輸出**：每一步記為「觀察（事實與證據）→ 推論（套用哪條規則）→ 結論（新事實與確定度）→ 下一步（檢查或行動）」。這個結構就是思考鏈；文字生成層（第 3 階段）負責把它說成人話，並可依需求展開或收合細節。
4. **約束與安全**：有風險的行動（改檔、刪除、送出）一律標示並要求確認（沿用離線訓練器現有的風險分級）；推理深度與步數有上限，防止無窮迴圈。

### 5.2 評估

- 每個推理領域附一組「案例：輸入事實 → 預期結論與鏈」測試；覆蓋「證據充分」「證據矛盾」「證據不足」三類。
- 指標：結論正確率、承認不確定的比例（不該猜的時候有沒有猜）、鏈中每一步是否可回溯到事實或規則。

### 5.3 成長方式

- AI 或使用者示範一次完整的思考過程（過程記錄來自對話與工具呼叫）→ 抽出可重用的規則與步驟模板 → 附範例驗證後存入。
- 規則被使用的次數與正確度被記錄；常用的提高優先權，常被推翻的標記待檢查。

## 6. 第 5 階段：小型本機模型（選項，未決定）

規則與模板做不到的部分（改寫、摘要沒見過的輸入、在規則沒覆蓋時提出假設）才考慮。做法不是訓練大模型：
- 用**已驗證的資料**當訓練與評測集：AI 成功解決的案例、規則與模板附的範例、使用者確認過的輸出。這些已經在累積（執行期知識附來源與範例）。
- 候選：瀏覽器內執行的小模型（WebGPU／WASM），負責「把事實與推理鏈改寫得更流暢」與「提出假設」，輸出一律經第 3 階段的事實一致性檢查，檢查不過就退回模板。
- 前提：第 3、4 階段先做完，因為小模型需要乾淨的結構化輸入與可驗證的輸出，否則只會產生看起來合理的錯誤內容。

## 7. 與現有程式的接點（為了不重工）

| 要做的 | 可重用的現有東西 |
|---|---|
| 事實層、確定度 | 離線訓練器的 pattern／規則分數（`_otPlan`）、RAG 檢索結果、診斷輸出 |
| 模板與槽位 | 現有的 `{名稱}` 填充（`_faOtFill`／`_faOtSlots`）、規則的 `what`／`cause`／`fix` |
| 語意比對（選模板、選規則） | `_faSemEmbed`／`_faSemCos`、`FA_SEM_GROUPS`（跨中英同義詞） |
| 規劃與多步驟 | 狀態機 `_faOtFsmRun`、steps、`FA_OT_TERMINAL` |
| 成長迴圈 | 待學習清單、`ref_define` 的「附範例才收」、匯出與 `promote-runtime-defs.js` |
| 蒸餾（從示範抽規則） | `_faOtDistill`（把成功的對話整理成規則、狀態機、語意 pattern） |

新增的部分應放在**獨立的領域無關模組**（例如 `renderer/src/gen/`，純函式，沒有任何領域字串），由離線訓練器呼叫；領域資料放在各自的 DSL／JSON。

## 8. 下一步（建議順序）

1. **定義事實的統一結構**（第 4.1 節的事實層），先讓現有的診斷輸出、API 語意查詢、錯誤碼查詢都能轉成它；這一步不增加新功能，但是後面所有通用能力的共同輸入。
2. **做領域無關的文件規劃與語句實現**：先支援 3 到 4 種文體（說明、步驟、問答、摘要），把診斷的 `summary`／`markdown` 改成用它產生，驗證輸出與現在一致，再擴到其他領域（證明它真的通用）。
3. **事實一致性檢查**與模板測試框架。
4. **推理引擎的前向推理與假設推理**，先用兩個**不同領域**驗證通用性（例如日誌診斷＋一個非技術的決策或規劃任務），避免做成診斷專用。
5. **成長機制通用化**：待學習清單擴到「任何離線處理不了的輸入」；從示範抽模板與規則（第 4.3、5.3 節）。
6. **多行規則（2026-10 已做第一版）**：領域知識這邊的補強（Python Traceback、核心 Call Trace、CMake 多行錯誤區塊），讓日誌診斷這個領域本身更完整。
7. 評估是否需要第 5 階段的小型模型。
