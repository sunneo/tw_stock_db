# 離線訓練器路線圖：隨使用成長，最終能離線生成文字與推理

> 2026-10-04。目標（使用者的方向）：離線訓練器**隨著使用而成長**；除了 pattern 規則（DSL）、gdb 錯誤診斷，也要能看懂 Linux journal 日誌、核心日誌、kernel panic；**最終**要能離線做文字生成與思考鏈。
> 這份文件說明「現在做到哪、下一步做什麼、為什麼這樣排」。**第 3 階段以後是規劃，還沒有實作**，不要當成已完成的功能。
> 相關：`DESIGN.reference-knowledge.md`（知識與日誌診斷的實作）、`DESIGN.offline-trainer.md`（離線訓練器本體）。

## 1. 成長的迴圈（已實作的骨架）

```
使用者貼日誌 ──► diagnose_log（規則比對）──┬─► 有規則：說明發生什麼事（根本原因、連帶結果、傳遞路徑、常見原因、怎麼處理）
                                           └─► 沒有規則的錯誤行 ──► 待學習清單（localStorage fa_ref_unmatched_v1，正規化後去重、計次）
待學習清單 ──► AI 擴充領域（offline_knowledge_expander）：查官方資料 ──► ref_define(build_error_rule, example, source)
                    └─ 規則必須附「一行真實日誌」，系統用它驗證規則真的比對得到，通過才收；收下後該行從清單移除
執行期規則 ──► /ref export ──► scripts/promote-runtime-defs.js ──► 人／Claude 覆核 ──► 進內建
```

設計重點：
1. **每一步都可驗證**：規則要附範例、錯誤碼要附來源、正規表示式要能編譯；壞的進不來。
2. **不確定就說不確定**：診斷找不到根本原因時，輸出「只看到連帶結果，要往上找第一個 error」，並列出沒有規則的行，而不是亂猜。
3. **越常見越先補**：待學習清單依出現次數排序，補規則的投資報酬率最高。
4. **知識與引擎分離**：知識是 DSL／JSON 文字檔（可 diff、可審查、可由 AI 產生），引擎是純函式。成長的是資料，不是程式碼。

## 3. 第 3 階段：離線文字生成（規劃，未實作）

現在的說明文字來自規則裡人寫好的句子，`summary` 與 `chain` 是「模板拼接」。要往「真正的文字生成」走，分三層，每層都先用規則和模板做，不用大型模型：

1. **事實層**：診斷輸出已經是結構化事實（系統、根本原因、連帶結果、檔案與行號、錯誤碼）。第一步是把這些事實統一成一個「事實圖」（節點：現象、原因、檢查、處理；邊：導致、需要檢查、解決）。
2. **文件規劃層**（content planning）：決定先講什麼、後講什麼、要不要合併重複原因、要不要提醒風險（例如「不要為了讓它通過亂改雜湊」）。用規則：嚴重度排序、同類合併、已知陷阱提示。
3. **語句實現層**（surface realization）：用模板加槽位填充（目前的 `{名稱}`），再加上：句型變化（避免每次都同一個樣子）、中英文雙語模板、依使用者程度調整詳細度（一行摘要／完整說明）。

驗證方式：不是看「像不像人話」，而是**事實一致性檢查**——產生的句子裡每個檔案名、行號、錯誤碼、數字都必須能回溯到輸入日誌或規則；回溯不到就不輸出。

## 4. 第 4 階段：離線推理鏈（規劃，未實作）

目標：不只說「是什麼原因」，而是像思考鏈一樣展示「怎麼推到這個結論」並能指出**下一步該查什麼**。

1. **假設樹**：每條規則的 `cause:` 本來就是一組候選假設。把它們變成節點，用日誌裡的證據加權（例如 `undefined reference to 'sqrt'` 讓「缺 -lm」的假設分數最高；`vtable for X` 讓「virtual 函式沒實作」最高）。
2. **鑑別性檢查**：每個假設附一條能區分它的檢查命令（`nm -C libfoo.a | grep sqrt`、`ldd`、`readelf -l`、`ls -l /sbin/init`），輸出「如果結果是 A 就是假設 1，是 B 就是假設 2」的決策步驟。
3. **推理鏈輸出格式**：觀察（日誌第 N 行說了什麼）→ 推論（這代表什麼）→ 檢查（跑什麼命令確認）→ 處理（怎麼改）。現在 `chain`（傳遞路徑）是它的雛形：它已經能說出「gcc 錯誤 → make Error 1 → BitBake 任務失敗」。
4. **互動式追問**：資訊不足時離線也能問「請貼上 config.log 的最後 30 行」，使用者貼了再繼續推（狀態機，離線訓練器已有 FSM 執行器 `_faOtFsmRun` 可重用）。
5. **證據不足時承認**：假設分數接近時不選邊，列出平手的假設與區分檢查。

## 5. 第 5 階段：小型本機模型（選項，未決定）

規則與模板做不到的部分（改寫、摘要不熟悉的日誌）才考慮。做法不是訓練大模型，而是：
- 用**已驗證的資料**當訓練與評測集：每次 AI 成功解決的案例（日誌→診斷→處理）、每條規則的範例、使用者確認過的結果。這些已經在累積（執行期定義附來源與範例）。
- 候選：瀏覽器內執行的小模型（WebGPU／WASM），只負責「把事實圖改寫成流暢文字」與「在規則沒覆蓋時提出假設」，且輸出一律經過第 3 階段的事實一致性檢查，檢查不過就退回模板。
- 前提：第 3、4 階段先做完，因為小模型需要乾淨的結構化輸入與可驗證的輸出，否則只會產生看起來合理的錯誤說明。

## 6. 下一步（建議順序）

1. **補規則量**：用待學習清單驅動，優先 Yocto／交叉編譯、核心驅動開發、容器環境常見的日誌；每週讓 AI 擴充領域跑一輪，覆核後升級成內建。
2. **多行規則**：支援「連續幾行一起比對」的規則（Python Traceback、核心 Call Trace、CMake 的多行錯誤區塊），把目前逐行比對的限制拿掉。
3. **事實圖與假設樹**：把規則的 `cause`／`fix` 結構化成可評分的節點（第 4 階段的基礎）。
4. **成長指標**：記錄「待學習清單的命中率」「同一行重複出現的次數」「規則被使用的次數」，用來看離線訓練器是否真的在進步，並找出該優先補的地方。
5. **從對話學習**：AI 在對話裡解決了一段日誌，但離線診斷沒有規則時，自動提示「要把這個做法存成規則嗎」（需要使用者確認，且仍要附範例與來源）。
