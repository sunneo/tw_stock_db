## 一、拆軌（Demucs）GPU 路徑

現況（這台是 i5-2320 加 GT 720，不是使用者的 Core Ultra 7 155U）：
- WASM 跑一個 7.8 秒片段約 20.9 秒（模型載入另外約 23.5 秒），這是正確的基準。
- GPU 圖執行器只有卷積與大型矩陣乘走 GPU，其餘運算在 CPU，每個運算都上傳再讀回，所以慢。
- 已發布 v586 修了「卷積分批派發輸出全 0」。之後的修正與量測都在分支 `claude/great-swirles-84aab9`，**尚未合併**（原因：整張圖的正確性還沒在真機驗證完，不能讓使用者先踩雷）。
- 分支上已驗證的點：第 659 個節點 GPU 17.46 秒、對 CPU 參考最大絕對誤差 1.2e-5；第 318 個節點的全零已修（派發超過 65535 個工作群）。

還沒做：
1. 第 1600、3200 個節點與全圖單片段的 GPU 耗時、逐軌最大相對誤差（超標一律算無效），結果對照 WASM 的 20.9 秒。
2. 常駐路徑補運算：卷積與反卷積、Softmax、LayerNorm、GroupNorm、Gather；驗證或拆掉未提交的一元運算與 Softmax 分支。
3. 輸出全零、含非數字的防線：全零或能量接近 0 要改走 WASM，並寫事件紀錄（現在只靠 150 秒看門狗）。
4. 可重用的量測與二分工具（Node 腳本，加工程模式裡的基準入口，輸出可貼回的摘要，給使用者的 155U 用）。
5. 執行期自適應：短探測、更細切、依 GPU 與版本記軟旗標、軟體轉接器直接不用 GPU。
6. 對照：ort-web 的 WebGPU 跑同一個模型、WASM 執行緒數掃描。
7. WebGL2 路徑接進執行期；F4；其他模型（SDXS、Kokoro 等）的運算覆蓋表與登記。
8. 使用者的 155U 實機驗證（這台無法代替）。

## 二、哼歌找歌與音訊轉 MIDI

現況：使用者實測播放原曲對著麥克風完全找不到，對照聽的 MIDI 像在亂找琴鍵。
- 已修：原曲指紋與判定的兩個門檻（有把握判定：乾淨 1/6→6/6、中等殘響 1/6→5/6、強殘響 0/6→4/6，模擬資料）。
- 已改：查詢端主旋律改用諧波和能量加連續性追蹤；Basic Pitch 音符再經主旋律選取（比直接用準很多）；n-gram 精確比對已接進搜尋；舊路線索引版本升為 4（快速旋律線仍是 3）。
- 模擬測試（32 首 MIDI 渲染，旋律單獨、無指紋）強殘響前 1 為 0.688、前 5 為 0.797。目標是前 1 至少 0.8、前 5 至少 0.95，**未達標**。

還沒做：
1. 真桌面版端到端評測（三路查詢轉譜乘比對乘和聲融合）的結果，選出預設查詢轉譜與模型沒下載時的退路。
2. 查詢端多聲部偵測實際接進搜尋；n-gram 加和聲色度的最終排序。
3. 真實歌曲驗證：使用者放 T-ara 的 TTL 對麥克風，確認找得到；對照聽的 MIDI 與原曲主旋律相似度。這需要使用者實機，模擬資料不能代替。
4. 舊路線索引需要重建的提示與自動重建在真機走一遍。
