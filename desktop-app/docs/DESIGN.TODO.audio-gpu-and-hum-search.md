## 一、拆軌（Demucs）顯卡路徑

### 現況（這台是 i5-2320 加 GT 720，不是使用者的 Core Ultra 7 155U）
- 使用者實際拿到的一直是 WASM 結果，正確。WASM 一個 7.8 秒片段約 20.9 秒（模型載入另外約 23.5 秒）。
- 同一個前綴（前 659 個節點）：顯卡 16.36 秒、WASM 4.58 秒。
- 顯卡路徑對 ORT 的 WASM 輸出**不正確**：第 659 個節點（第一個真正走顯卡的卷積）最大誤差 0.525。之前的「通過」比對的是圖執行器自己的 JavaScript 參考，不是 ORT，全部不採信。
- 架構問題：現行是「處理器為主、逐運算把資料送去顯卡再拿回來」，讀回上千 MB（輸出只有幾個值）。應改成「顯卡常駐、只讀回輸出」，像我們自己的 `qwen_gpu.js`。
- 已發布 v586 修了分批卷積輸出全零。後續全部在分支 `claude/great-swirles-84aab9`（未併入，約 43 個提交），**不可整支併入**，理由：正確性未對 ORT 驗過。

### 順序（前一步沒過就不做下一步）
1. 找第 659 個節點對 ORT 誤差 0.525 的根因：同一個輸入，ORT 單節點、JavaScript 參考、顯卡三方比對。之後所有驗證真值一律是 ORT 的 WASM 輸出。
2. 讀回歸因：每次讀回記位元組、產生節點、迫使讀回的下游運算，前十名；區分必要讀回（圖輸出、抽樣）與回退讀回；估算全部常駐後的讀回量。
3. 紙上評估（決定要不要做的關卡）：整圖總運算量、激活與權重資料量、屋頂線下限與可達比例估計。估計不到 WASM 20.9 秒的一半就停，寫「不值得」。
4. 運算覆蓋盤點：已有常駐實作、已有範本沒接（`ix_kernel.js` 的切片、切分、轉置、擴展、補邊、串接）、完全沒有。**全有或全無**：有任何運算沒覆蓋，整張圖走 WASM，不再混合。
5. 編譯式常駐計畫原型（只做第 659 個節點前綴）：依序排好派發清單、依活躍區間預先配置並重用緩衝、權重只上傳一次且跨片段快取、少數幾次提交（每次不超過 300 毫秒預算）、只讀回輸出。成功門檻：對 ORT 正確，且同前綴比 WASM 快 2 倍以上；達不到就停止並寫報告。
6. 卷積核心效率：用顯卡時間戳查詢拆開核心執行、上傳、讀回、同步；確認有多少卷積真的在顯卡上算（常駐卷積只支援群數 1、批次不超過 8）。
7. 可攜量測工具（Node 腳本加工程模式基準入口，輸出可貼回的摘要，含轉接器資訊），讓使用者在 155U 上實測。**若 155U 實測顯示顯卡沒有優勢，整條線停止。**
8. 安全網整理成可單獨合併的小提交：裝置遺失明確丟錯並退回、輸出非數字、能量近零、超時（4 倍 WASM 基準）退回、單次提交預算。這些對使用者是純好處，與其他改動分離後才能先合併發布。

### 優先在 WASM 側（真正會跑的路徑），都還沒量
- 執行緒與向量指令（跨來源隔離、執行緒數掃描）。
- 8 位元整數量化（拆軌品質要用客觀指標驗證）。
- 模型載入 23.5 秒比單片段還大：快取推論工作階段、預先轉 ORT 專用格式。
- 檢查片段重疊比例、位移平均次數、六軌是否都需要。
- 多個片段平行（多個背景工作緒）。

### 流程規則（來自這次檢討）
- 任何「效率差幾倍」的說法，先寫屋頂線（算力、頻寬、可達比例）與被測運算的運算量、資料量，再看實測。
- 耗時要能拆成核心執行、上傳、讀回、同步；沒有顯卡時間戳不下效率結論。
- 比較對象永遠是使用者實際會走的路徑，輸出先過對該路徑的正確性檢查才談速度。
- 長時間測試前先做紙上估算並核對硬體規格。
