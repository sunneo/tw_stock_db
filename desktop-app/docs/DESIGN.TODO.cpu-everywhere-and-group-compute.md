## TODO 1：不經 cudaweb 的 CPU 路徑也要吃到優化

### 現況（已查證，2026-11-19）
- 新的 CPU 矩陣乘核心（`renderer/src/gpu/cpu_gemm*.js`，WASM SIMD、分塊打包、多核、原地轉置、卸載給 CPU）**只接在 `mm_ops` 的矩陣乘**。單核實測約 7.5 到 12.6 GFLOP/s（i5-2320，4 核 4 執行緒，只是這台的數字）；4 個工作者的擴展不穩定（2.7 倍與 1.25 倍各出現兩次，原因未查）。
- LLM、生圖、VLM 等離線模型走 transformers.js 或 onnxruntime-web 自己的 WASM／WebGPU 運算核心，**沒有經過**新核心（見 `docs/COVERAGE.cudaweb-models.md`）。
- 其他運算（`q8mm`、`MatMulNBits`、注意力、卷積、softmax、層正規化）沒有 CPU 優化路徑。

### 要做的事
1. **先量，不要先接**：量 onnxruntime-web WASM 的矩陣乘與 `MatMulNBits` 速度（單核、多核、SIMD 與非 SIMD），與 `cpu_gemm` 同一形狀比較。onnxruntime-web 本身可能已有 SIMD 與多執行緒；新核心不明顯更快就不取代（量到什麼寫什麼）。
2. **接入方式的選項**（先評估再選，不要直接動 ORT 內部）：
   - 讓 cudaweb 的圖形工作階段（`renderer/src/gpu/graph_session.js`，不支援的算子就丟錯、退回原工作階段）新增 **CPU 後端**：MatMul、Gemm、MatMulNBits、卷積（im2col＋矩陣乘）、逐元素、softmax、層正規化走自家的 SIMD 核心；不支援的算子退回原工作階段。
   - 對 transformers.js：同一個圖形工作階段包裝，失敗就退回原路徑。
3. **向量化與記憶體**：逐元素與規約（softmax、層正規化、RMS、激活函數）也做 `f32x4` SIMD；轉置用面板打包時順便轉置，原地轉置只在呼叫端允許覆寫時用，預設絕不改動輸入。
4. **清單（包括但不限於）**：Qwen3（網頁、桌面原生）、Florence-2、SmolVLM、LLaVA、SDXS 生圖、Whisper、Kokoro、MOSS、e5 嵌入、離線翻譯、深度、分割、姿態、ECAPA。
5. **驗收（每個模型各自）**：對原路徑的輸出誤差（相對誤差，f32 在 1e-5 內；量化模型另訂）、端到端耗時（中位數、先暖機、標硬體）、記憶體峰值；**沒有量到好處的標「沒有好處」，不留著增加複雜度**；預設關，量到好處再由使用者決定是否預設開。
6. 網頁版與桌面版都要驗（網頁版沒有 `SharedArrayBuffer` 時退回單執行緒或複製）。

### 已知風險
- 把 ORT 換成自家解譯器，速度可能反而變慢（解譯成本、缺融合算子）；一定要先量。
- 精度：SIMD 的累加順序與 KC 分塊會影響誤差（已出現 K=512 時 1.26e-5，改 KC=64 才進 1e-5）。

## TODO 2：群組分散網路計算（跨節點 offloading）

### 目標
群組內願意貢獻 CPU 或 GPU 的成員，共同承擔離線模型的工作量，把自己的離線模型連線共享給群組；節點多了、分層有利時，可以取用更大的模型。這是**跨節點的 offloading，不是傳球遊戲**；概念是 distributed-llm 與 air-llm 的混合，再加上每個節點內部的 heterogeneous computing（CPU＋GPU，已有 `hetero_split`、`hetero_rates`、Profile）。

### 使用者描述的模型（逐點，尚未驗證可行性）
- 群組內所有被配置來計算的節點**指向同一個離線模型**；可以分批貢獻不同模型（例如大家都用 Qwen3-0.6B，節點多了再換更大的）。
- 分散負載的方式是 **context 共享**：對話 context 一起分散共享，**每個節點指向自己要計算的分層**。
- 中間計算結果需要「遮罩」之後再算的，就算一次同步；**網路成本必須算進決策**。

### 設計要先弄清楚的事
1. **「遮罩」是什麼意思**：使用者原話是「需要將中間計算結果做一次遮罩在算的就算一次同步」。我的猜測（**未向使用者確認**）：指注意力遮罩那類需要全部位置資訊的步驟，或需要前一層完整輸出才能繼續的邊界，每次跨節點邊界就是一次同步。**請使用者確認或更正。**
2. **切法**：管線切分（每個節點持有連續的幾層，激活值一站傳一站）是最符合「每個節點指向自己要計算的分層」的做法；每個節點只需載入自己那幾層的權重（air-llm 式逐層載入）與那幾層的 KV 快取，context（詞元）在群組內共享。
3. **網路成本模型（先寫出來，再決定值不值得）**：
   - 解碼時每個詞元要過每個節點邊界一次，延遲約為「節點數 × 單趟往返延遲」，所以跨網際網路時每秒詞元數的上限很低（例如 4 個節點、單趟 50 毫秒，上限只有幾個詞元／秒；這是估算，要用實測的延遲取代）。區域網路才可能划算。
   - 前填（長提示）是頻寬受限：每個詞元每個邊界傳一個隱藏向量（例如隱藏維度 1024 的 f16 約 2 KB／詞元／邊界，**依模型而定**）。
   - 決策：只有「分層後單節點算得更快的收益」大於「額外的網路延遲與傳輸時間」才分散；否則留在單節點。需要實測鏈路延遲與頻寬，沿用 `hetero_rates` 的速率快取概念（鍵含節點與鏈路）。
4. **分層的分配**：依每個節點實測速率（Profile 已能量 CPU／GPU 的端到端速率）與記憶體上限，按比例分配層數；節點增減時重新分配。
5. **異質與精度**：不同裝置（CPU、各種 GPU、量化格式）浮點結果不完全相同，邊界處的激活值精度與傳輸格式（f16 或量化）要定；跨節點結果與單節點結果的誤差要有上限。
6. **信任、隱私與安全（使用者尚未規定，必須先決定）**：
   - 節點會看到提示內容或其中間激活（可能被還原），所以只限信任的群組，要有邀請與身分驗證，傳輸要加密。
   - 惡意或出錯的節點回傳錯誤結果：需要抽樣重算或冗餘比對。
   - 貢獻是自願、可隨時退出，有資源上限（CPU／GPU 使用率、電量、時段）。
7. **連線**：網頁版與桌面版之間的點對點連線（WebRTC 資料通道與訊號伺服器？區域網路直連？）、穿越 NAT；**先查專案現成的**（工具清單裡有 `delegate_to_machine`、`list_remote_machines`，以及瀏覽器控制伺服器，是否可重用都沒查）。
8. **節點中途離線**：該節點的層要由別的節點接手；KV 快取遺失要重算（需要重新前填），或層冗餘；先定策略。
9. **多個對話與批次**：多個使用者同時用時，要批次化攤薄每個邊界的延遲；排程公平性。

### 分階段（建議）
- **P0 設計與量測（單機模擬）**：在同一台機器上用兩個到四個「虛擬節點」（各自的工作者）切分 Qwen3-0.6B 的層，驗證跨節點結果與不切分的結果一致（誤差上限），並量出邊界傳輸的資料量與延遲模型；寫出網路成本公式。**這一步完成前不碰真網路。**
- **P1 區域網路兩個節點**：真的跨機器，只做管線切分，量每秒詞元數與單機比較；沒有收益就如實記。
- **P2 群組管理**：建立、邀請、加入、貢獻設定、資源上限、節點狀態。
- **P3 較大模型與動態分配**：節點增加時取用更大的模型（需要逐層載入與權重來源）。
- **P4 容錯與驗證**：節點離線、結果抽驗。
- 每一階段都要有 node 測試（假節點與假網路延遲）與真機驗證，沒有收益的階段不繼續。

### 需要使用者決定
1. 上面「遮罩」的意思。
2. 群組的信任範圍：只限同一個人的多台機器？朋友群組？還是公開？這決定安全設計的深度。
3. 是否接受「跨網際網路時速度可能比單機更慢」，並只在區域網路預設啟用？
