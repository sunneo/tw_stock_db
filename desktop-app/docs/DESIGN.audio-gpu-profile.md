# Demucs 在 WebGPU 圖形引擎上的真機量測（診斷報告）

日期：2026-11-26　範圍：桌面版（Electron）、Demucs 6 軌拆軌、cudaweb GPU 圖形 session

## 結論（目前能下的）

1. 在這台機器上，GPU 路徑的第一段推論**超過 150 秒仍未完成**，看門狗把它切掉並退回 WASM。因此「GPU 比 WASM 慢」目前是**看門狗觸發**的結果，不是 GPU 路徑「算完但比較慢」。
2. 第一段是否大部分是一次性成本（著色器編譯、權重上傳），**這次量測無法判定**：第一段被看門狗中斷，沒有第二段 GPU 資料。
3. 退回 WASM 後的暖機段約 22.7 秒（7.8 秒音訊），與網頁版 WASM 約 45 秒的先前數字同一量級，這裡只量到一個段，不能下更精確的比較。
4. 尚未做：逐層計時鉤子、三路徑數值比對（與 WASM 的最大誤差）、onnxruntime-web webgpu 路徑的量測、看門狗修改。本次沒有修改任何來源程式。

- features：只有 `subgroups`，**沒有 shader-f16**。

## 看門狗判定是否過於悲觀（第 3 項）

目前程式（`renderer/src/floating-assistant.js` 的 `_audioGpuSession`）對每段推論做整段 150 秒計時，超時就寫入 `audioGpuSlow:<模型id>` 旗標，之後該模型一直走 WASM，直到使用者重置 GPU 設定。

- 這次量測顯示：在這台機器，第一段就超過 150 秒，所以看門狗**確實觸發了**，但這不能證明後續段也會那麼慢。
- 沒有資料前，不建議直接放寬或改成暖機後計時；應先做一次「允許第一段跑完」的量測（需要另外的評測設定，本次未做）。
- 旗標永久生效也是問題：一次超時就讓之後所有拆軌都回 WASM，直到手動重置。這是設計問題，與量測結果無關，應另行討論。

## 副作用與注意事項（必讀）

- 評測運行時，`audioGpuSlow` 旗標已經存在於 localStorage（第 1 次量測即見），而評測用的是全新 `--user-data-dir`，代表這個旗標**不是存在這個隔離的 profile 裡**，可能寫在使用者實際的設定中。第 2 次執行更新了它的時間戳與原因字串。
- 我沒有清除該旗標（因為可能影響使用者實際設定）。若要還原，需要先確認它實際存放的位置。
- 第 2 次的評測在記憶體中忽略該旗標，只影響該次執行，不寫入儲存空間。

## 尚未做的建議（有證據支持的方向，但未實作）

1. 量一次「允許第一段跑完」（移除或放寬看門狗，只在這次評測中），分開記錄第一段與第二段時間，才能判斷是否一次性成本。
2. 加一個預設關閉的逐運算計時鉤子（卷積、矩陣乘、重排、上傳、讀回）。
3. 與 WASM 的輸出做數值比對（最大誤差），目前只確認 6 軌都產出。
4. 若 GPU 第二段仍遠慢於 WASM，應把 onnxruntime-web webgpu 作為後備的候選，與圖形引擎比較。
5. shader-f16 不存在，f16 路線不可行，不應列入短期方案。
