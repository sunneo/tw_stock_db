## 2. 一步的派發清單（由程式碼逐行對照得出，已用真實 L 規模的計數 367 對帳）

每層（`L` 層）的前向（`full_param_step_device.js` 341–368 行）：

| 項目 | 次數／層 | 說明 |
|---|---|---|
| rmsnorm n1 | 1 | 列寬 d |
| matmul Wq、Wk、Wv | 3 | |
| qk-norm 的 q、k rmsnorm | 2 | qkNorm 時 |
| RoPE q、k | 2 | `rp` |
| transposeTH k | 1 | |
| attnFwdKt | 1 | 注意力核心（屬 cudaweb-train-backend，不動） |
| transposeTH v | 1 | |
| matmul Wo | 1 | |
| axpy 殘差 h1 | 1 | |
| rmsnorm n2 | 1 | |
| matmul Wg、Wu | 2 | |
| silu、mul | 2 | `a = silu(g)∘u` |
| matmul Wd | 1 | |
| axpy 殘差 | 1 | |

前向合計約 **22 次／層**。

每層的反向（369–410 行）約 **41 次／層**，包含 MLP 反向（da、dWd、mlpBwd、dWg、dWu、dg·Wg、du·Wu、axpy）、增益梯度（每個 `gainGrad` 是 rmsnorm＋mul＋matmul 共 3 次，每層 4 處共 12 次）、rmsnormBwd（每層 4 次）、attnBwdVt（3 次）、RoPE 反向（2 次）、Wo／Wq／Wk／Wv 梯度與 dn1 累加。

每步的固定部分：
- 嵌入查表 gather 1 次、交叉熵與頭部約 5 次、嵌入 scatter 1 次。
- **優化器（每個參數張量各 2 次）**：`sumsqSlot` 1 次＋`adamwCoef` 1 次，共 `2 × 參數張量數`。L 類有 46 個參數張量，所以這一段就有 92 次；加上 `sumslots` 與 `clipCoef` 2 次。這是目前最大、最容易合併的一塊。
- K＝1 時 `scal` 不派發（已在程式碼中省略）。

對帳（真實 L 設定，4 層）：4 × (22＋41) = 252；優化器 46 個參數張量 × 2 = 92，再加 sumslots、clipCoef 共 2；頭與嵌入約 21（gather、交叉熵、頭部、增益梯度、scatter）。合計 367，與實測 367 相同。頭與嵌入的細項 21 次尚未逐項核對，只是由總數推算。

## 3. 合併候選（每項「省幾次」都尚未量測）

1. **優化器的平方和與 AdamW 批次化**（最大項，每張量 2 次，L 類 92 次）。
   - 障礙：WebGPU 每個核心的 storage 綁定數有上限（`gpu_core.js:724` 預設 8，請求提高到最多 16），不能一次綁 46 個張量。
   - 由上限推得的粗上限（**未量，是綁定數算出的理論值**）：sumsq 每張量 1 個綁定＋parts，約 14–15 張量一次，46 張量約需 4 次；AdamW 每張量 p、g、m、v 4 個綁定＋cf，16 綁定時約 3 張量一次，46 張量約需 16 次。合計約 20 次，比現在 92 少約 72 次。實際能不能達到要先驗證。
   - 數值：若每個張量仍用同一段逐元素運算（sumsq 的歸約順序、AdamW 的每元素式子不變），結果應與現在**逐位相同**，不改累加順序。這是要驗證的假設，不是已證明的事實。若要把多個張量的平方和合併成一次歸約，順序會變，就不符合要求，不採用。
   - 候選做法：把所有參數、梯度、動量、變異數合成四條扁平緩衝區（一次性配置），用偏移表。這是常駐狀態的大改，需要改 `makeResidentState`、`readResident`、`loadResident`，要另外對拍檢查點。
   - 未量。
2. **殘差加法＋rmsnorm 合併**：`axpy` 後接 `rmsnorm`（n2）是資料相依的，但可寫在同一核心內（先算 h1 再歸一化，h1 寫出一次）。每層可省 1 次，未量。
3. **增益梯度的 `gainGrad` 三次派發**（rmsnorm＋mul＋matmul）：可合成一個逐列歸約核心，輸出列加總。每個 gainGrad 可省 2 次，每層 4 處，共 8 次／層，未量。融合核心若寫成大核心要留意暫存器用量，要量。
4. **RoPE q、k 合併為一次派發**（同一個核心處理兩個輸入），每層省 1 次，未量。
5. **silu＋mul**：`a = silu(g)∘u` 可合成一次，每層省 1 次，未量。

資料相依、必須分開的：matmul 之間（前一個輸出是後一個輸入）、注意力前後的轉置、反向中 dq／dk 進 RoPE 反向與 qk-norm 反向的順序。

### 3.1 阻礙（第二輪，2026-11-29）

- 假裝置（`gpu_fakes.js`）只認得已有的核心名稱（靠 `// @kernel` 標記分派），新的批次核心沒有對應的 CPU 參考分支，**無法用假裝置對拍**。這個檔不在 disp 負責範圍，要由管理者或 mm 決定是否加分支。
- 因此對拍只能在真實 GPU 上跑（取鎖）。這一輪沒有取鎖，沒有實作評估版核心。
- 結論：優化器批次化的評估版**尚未實作**，數字只有上面的理論上限，不能當成效果。

## 9. AdamW 批次提案（尚未進產品檔）

現況：每個參數張量一次 `adamwCoef`（L 規模 46 次、XL 68 次）。每張量的綁定數：p、g、m、v 四個 storage 加共用的 cf。

綁定上限是本機實測的 8（規範最小值），所以在 8 下：
- 方案 A（依綁定上限分組，不動常駐狀態）：每次派發 K = ⌊(limit−1)／4⌋ 個張量。limit＝8 時 K＝1，**沒有減少**；limit＝16 時 K＝3。實作在 `full_param_fused.js` 的 `adamwMultiDispatch`，已在假裝置通過等價測試（綁定上限 8 與 16 的參數、動量、方差雜湊與原版相同）。限制：本機上限是 8，方案 A 在這台機器上不會減少派發。
- 方案 B（m、v 放進扁平 arena，p 與 g 仍各自綁定）：每張量 p、g 兩個 storage，加 m、v arena 與 cf 共 4 個共用，所以 K＝⌊(8−4)／2⌋＝2，L 規模約 23 次（由綁定數推算，未實測）。需要動：`makeResidentState`、`readResident`、`loadResident`（常駐狀態布局）與檢查點格式（需維持每個名稱的讀回形狀）。
- 方案 C（p、m、v 都進 arena，梯度也連續配置）：需要 nn_ops 的矩陣乘輸出偏移（屬 mm 範圍），本提案不採用，除非 A、B 的實測收益不足而且確認要做。

逐位相同：每元素的運算式不變，所以理論上逐位相同；檢查點格式在方案 A 不變，在方案 B 需要讀回時切片回每個名稱（格式不變，但內部布局變）。

收益門檻：小於約 1 ms／步（L）不值得。需要實測：批次 3 的 v2 量測（方案 A 的 K＝3，只在綁定上限 16 的裝置上有收益）。本機為 8，所以方案 A 在本機的實測收益為 0，這是確定的（派發數不變）。方案 B 尚未寫原型，收益未量。

結論（目前）：方案 A 不進產品（本機沒有收益）；方案 B 需要先做原型並量測，若收益 ≥1 ms／步再提案改動常駐狀態。
