# 拆軌（Demucs）：顯卡路徑為什麼慢、演算法能不能優化

日期：2026-11-26～27。量測機器：處理器 i5-2320，顯卡 GT 720（約 0.3 兆次浮點運算每秒）。
這**不是**使用者的機器（Core Ultra 7 155U 內顯），所以結論只對這台成立。
模型：htdemucs 六軌，權重 fp16（136 MB），單一片段 7.8 秒（374400 個樣本，48000 赫茲）。

證據標記：【實測】有數字與出處；【假設】沒有量到，只是推論。

## 一、結論

1. 在這台機器上，**WASM 比顯卡路徑快**，而且快得多。同一個前綴（前 659 個節點）：顯卡 16.36 秒、WASM 4.58 秒，WASM 快約 3.6 倍。【實測】
2. 整個片段 WASM 只要 20.9 秒（模型載入另外 23.5 秒）。顯卡光前 1600 個節點就 22.9 秒，前 3200 個節點 77 秒，全圖 24819 個節點、後段還有更重的矩陣乘。外推顯卡整段遠超 20.9 秒。【實測加外推；整段未實測】
3. 顯卡路徑**不能算準確**：對真正的基準（ORT 的 WASM 輸出），第 659 個節點（第一個真正走顯卡的卷積）最大誤差 0.525，遠超門檻 1e-4。之前所有「誤差很小」的通過，比對的是圖執行器自己的 JavaScript 參考，不是 ORT，因此「彼此一致卻都錯」的可能性存在。【實測；根因未找到】
4. 使用者實際拿到的拆軌一直是 WASM 退路的結果，是正確的。

## 二、為什麼慢（各原因與證據）

### 原因一：每個運算都在處理器與顯卡之間搬資料【實測，是最大的一塊】
- 前 1600 個節點、張量不常駐：上傳 1254 MB、讀回 883 MB。
- 逐元素運算本身算力需求極小，但耗時很大：乘法 17.0 秒（141 次）、加法 10.9 秒（83 次）、Erf 6.7 秒。時間幾乎全是搬運與同步。
- 讓張量留在顯卡（常駐）後，前 1600 個節點由 71.1 秒降到約 35 秒（該數字當時的輸出有錯，見原因五，只能當方向參考）。
- 之後修正正確性、加上其他改動，前 1600 個節點為 25.04 秒，再讓 Sigmoid 常駐為 22.88 秒；讀回量仍約 1500 MB，表示搬運還沒消除。

### 原因二：派發次數不是主因【實測】
- 前 659 個節點的卷積派發由 1763 次降到 272 次（改成切塊矩陣乘），耗時只由 61.9 秒降到約 58 秒。

### 原因三：卷積耗時遠高於「理論下限」——但這個比較本身有問題，見第六節檢討【已更正】
- 原先的寫法：前 1600 個節點的卷積約 51 G 次乘加（約 102 GFLOP），以 0.3 兆次每秒計「理論下限」約 0.34 秒；實測約 18～20 秒，「差約 55～60 倍」。
- **這個「55～60 倍」不能當結論**：
  1. 拿的是峰值算力，沒有考慮記憶體頻寬（屋頂線模型）。依本機規格：顯卡 GT 720 可用記憶體頻寬約只有十幾 GB 每秒（2 GB 版本通常是 64 位元 DDR3，約 14 GB/s，本機沒有核對是 DDR3 還是 GDDR5），卷積展開後的矩陣乘每次乘加若沒有充分重用就要讀兩個浮點數，51 G 次乘加最壞約 400 GB 的記憶體流量，以十幾 GB/s 計就是約 30 秒，與實測 18～20 秒同量級，所以更可能是**頻寬受限、核心沒有做好重用**，不是「差 55 倍算力」。【推論，未用顯卡時間戳驗證】
  2. 實測的 18～20 秒是「卷積運算」的牆鐘時間，包含上傳輸入、同步、讀回，不是核心執行時間；沒有用顯卡時間戳查詢，無法分開。【方法缺陷】
  3. 沒有確認這 51 G 次乘加是否全部真的在顯卡上算：常駐卷積只支援群數 1 且批次不超過 8，其餘卷積仍在 JavaScript（處理器）算，混在同一個耗時裡。【未驗證】
  4. 其中部分執行是輸出全零的錯誤版本，耗時不具代表性。

### 原因四：單次提交太久，Windows 會重置顯卡【實測】
- 前 3200 個節點的兩次執行都在一開始崩潰，事件紀錄為 `DXGI_ERROR_DEVICE_HUNG`（0x887A0006），是顯卡逾時偵測（約 2 秒）。
- 因此單次提交預算降到 300 毫秒，提交次數隨之增加。

### 原因五：路徑上有三個正確性錯誤，都讓輸出變成全零或錯誤【實測，前兩個已修】
1. 注入的 WGSL 識別字以雙底線開頭（保留字），分批卷積輸出全零。已修，已發布（v586）。
2. 常駐卷積展開只用單一維度派發，工作群超過 65535 時被拒絕，後面矩陣乘讀到零（前 318 個節點）。已修（`30b5ae520`，在分支上，未併入）。
3. 第 659 個節點卷積對 ORT 誤差 0.525。**未修，根因未知。**

### 原因六：節點太多、單個運算都很小【假設】
- 全圖 24819 個節點，每個都有派發、同步與記憶體配置的固定成本；顯卡要靠大量並行才划算，小張量吃不到。這一項沒有單獨量測。

## 三、演算法有沒有可能優化

先講結論：**有，但投資報酬率最高的是 WASM 這邊，因為它是真正會跑的路徑。** 顯卡路徑要先修正確性，再值得談優化。

### A. 讓 WASM（使用者實際會跑的）更快——建議優先【多數為假設，需要實測】
1. **執行緒與向量指令：** ORT 的 WASM 若能用多執行緒（需要跨來源隔離，Electron 可以設定）加 SIMD，通常有數倍差異。要做執行緒數掃描，量出最佳值。
2. **量化：** 把權重量化成 8 位元整數。ORT WASM 的整數矩陣乘通常明顯快、記憶體也少，但拆軌品質會變，需要用已有的人聲與其他軌的客觀指標驗證，不能憑感覺。
3. **模型載入 23.5 秒比單一片段 20.9 秒還大：** 快取已建立的推論工作階段，一首歌 23 個片段只載入一次；預先轉成 ORT 專用格式（.ort）可縮短載入。
4. **工作量本身：** 檢查現在用的片段重疊比例、是否做了多次位移平均、輸出六軌是不是都需要；若只為了轉 MIDI，可以考慮四軌模型或只取需要的軌。這些是用品質換速度，要先量。
5. **多個片段平行：** 用多個背景工作緒同時跑不同片段，吃滿處理器核心數。

### B. 讓顯卡路徑有機會贏——只在使用者的 155U 實測有希望才值得做
1. **運算融合：** 把 GELU 鏈（除、Erf、加、乘、乘）、組正規化加激活、卷積加偏置加激活，各合成一個核心。逐元素運算的搬運與派發成本（原因一）幾乎可以全部消除。這是顯卡路徑最大的單一改善空間。
2. **整圖編譯成少數幾次提交：** 像 ORT 的 WebGPU 執行環境那樣，把子圖一次排進同一個命令緩衝，張量全程留在顯卡，只在輸出才讀回。
3. **卷積改用隱含矩陣乘（不先展開）或 Winograd：** 核心大小 3 的卷積用 Winograd 可以少約 2.25 倍乘法；隱含矩陣乘避免寫出巨大的展開緩衝。
4. **半精度：** 若轉接器支援 `shader-f16`，記憶體流量減半。GT 720 這種舊卡大概不支援。
5. **先和 ORT 的 WebGPU 執行環境比：** 它已經做了上面多數事，如果它在使用者機器上都沒贏過 WASM，我們自己做更不可能贏。

### C. 不建議
- 繼續在這台 GT 720 上為提速調整顯卡路徑：算力太低，即使做完融合，上限也不一定贏過這台處理器的 WASM。

## 四、還沒做、需要的下一步（只列真正沒做的）

2. 第 1600 個節點對 WASM 的同條件並排表。

5. 可單獨合併的安全網提交（裝置遺失、輸出非數字、能量近零、超時退回）整理清單。

## 五之一、本機規格與「顯卡應該遠比處理器快」的預期
（本機 Windows 查詢）處理器 i5-2320，4 核、3.0 GHz（加速 3.3 GHz），內建 AVX 但沒有 FMA 與 AVX2；記憶體兩條 8 GB DDR3-1333（雙通道，約 21 GB/s）；顯卡 GT 720，2 GB。

粗估峰值（理論值，實際會更低）：
- 處理器原生 AVX：4 核 × 每週期 16 次浮點 × 3.0 GHz ≈ 190 GFLOPS。WASM 只有 128 位元向量指令，約為一半，≈ 96 GFLOPS（前提是 4 個執行緒都用上；ORT 在這裡實際用幾個執行緒沒量過）。
- 顯卡 GT 720：約 0.3 TFLOPS（300 GFLOPS，規格值）。
- 頻寬：處理器約 21 GB/s；顯卡約十幾 GB/s（版本不明）。

結論：**這台的顯卡在紙面上只比處理器快 1.5～3 倍，頻寬甚至不比處理器大。** 所以「這台的 GPU 應該會遠比 CPU 快」這個預期一開始就不成立；再加上每個運算要搬資料的固定成本，輸給 WASM 是預期內的結果，不需要靠長時間測試才發現。使用者的 155U 內顯與本機是不同的硬體，結論不能直接套用。

## 六、檢討：「卷積差 55～60 倍」這個說法錯在哪裡
1. **用錯的上限。** 拿峰值算力當下限，卻沒有算記憶體頻寬。卷積加矩陣乘這類運算在低階顯卡上通常受頻寬限制，正確做法是先算屋頂線（算力與頻寬兩個上限取較低者）。這是幾分鐘就能做完的紙上分析，卻拖到做了很多小時的實測後才發現。
2. **把牆鐘時間當成核心時間。** 沒有顯卡時間戳查詢，無法把核心執行、上傳、讀回、同步拆開，卻直接下「效率」的結論。
3. **沒有確認被測的運算真的在顯卡上。** 常駐卷積只支援群數 1、批次不超過 8，其餘走 JavaScript。把兩者混在一起量，等於沒有量。
4. **沒有核對硬體。** 使用者說「這台的顯卡應該遠比處理器快」，我沒有先查規格就接受了前提，後面所有「還差幾倍」都建立在這個沒驗證的期待上。
5. **真值選錯。** 準確度一直拿圖執行器自己的 JavaScript 參考當標準，沒有用 ORT 的 WASM 輸出，所以「精準度可接受」的結論無效。
6. **在錯誤版本上量耗時。** 輸出全零時量到的快，被當成進步回報給使用者。

### 之後的做法（寫進流程）
- 任何「效率差幾倍」的說法，先寫出屋頂線（算力、頻寬、實際可達比例）與被測運算的運算量與資料量，再看實測。
- 耗時一律要能拆成：核心執行、上傳、讀回、同步；沒有顯卡時間戳就不下效率結論。
- 比較對象永遠是使用者實際會走的路徑（這裡是 ORT 的 WASM），且輸出要先過對該路徑的正確性檢查，才能談速度。
- 開始長時間測試前，先做便宜的紙上估算，並先核對硬體規格。
