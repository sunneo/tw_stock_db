# P1 速度與屋頂線（全參數訓練，2026-11-28）

量測方式：Electron 真機（`scripts/eval/gen_full_param_cudaweb_eval.js` 產生的評估檔，獨立 `--user-data-dir`，埠 17931）；cpu-py 用 `llm_scratch.LM`（torch f32，4 執行緒，獨立 Python 行程）。
設定：V=2048、d=256、L=4、H=8、kvH=4、F=512、T=128、qk-norm。隨機初始化，暖機 1 步後量 3 步取平均。**這是速度量測，不是對拍**（對拍用 fp64 fixture，見 PLAN）。

| 路徑 | 每步牆鐘 ms | 矩陣乘 ms（呼叫數） | GPU 逐元素 ms（呼叫數） | 其餘 CPU ms |
|---|---|---|---|---|
| cudaweb（矩陣乘＋前向逐元素＋AdamW 在 GPU，反向逐元素在 CPU） | 3379 | 1743（87） | 1211（79） | 425 |
| 純 JS（CPU，f64） | 3924 | 3290（87） | 184（79） | 450 |
| cpu-py（llm_scratch.LM，torch f32） | 111 | 整段 torch，未拆 | — | — |

損失：cudaweb 與純 JS 的前 3 步一致到約 1e-6（6.91132 對 6.91133）。

**屋頂線**（同一設定）：每步 2.416 GFLOP（矩陣乘，前向＋反向≈3×前向）；參數 11.5 MB（f32）。
- 運算下限（0.3 TFLOPS，GT 720 量級峰值）：每步 ≥ 8.1 ms。
- 記憶體下限（14 GB/s，每步約 6 次參數量的讀寫）：每步 ≥ 5.0 ms。
- 實際有效速率：cpu-py ≈ 22 GFLOP/s；cudaweb ≈ 0.7 GFLOP/s；純 JS ≈ 0.6 GFLOP/s。

**瓶頸（拆解）**：
- cudaweb 每步共 166 次 GPU 呼叫（矩陣乘 87＋逐元素 79），平均每次約 15–20 ms；這些呼叫就佔了 2.9 s 的 3.4 s。
- 每次呼叫都是一次獨立的「上傳、提交、等待、讀回」，所以成本是**每次呼叫的固定開銷**，不是運算本身。
- 運算本身遠低於屋頂線（每步 2.4 GFLOP，理論 8 ms）。
- **分項無法精確拆成核心執行、上傳、讀回、同步四段**：沒有用 GPU 時間戳查詢（timestamp query），只能量到每次呼叫的牆鐘。這一項未完成，原因是執行期沒有暴露時間戳 API；要量的話需要改 `nn_ops.js`／`mm_ops.js`（屬於他人維護的核心，不在本階段改）。

**結論與下一步（不是「做不到」）**：
- 要讓 cudaweb 追上屋頂線，必須把整步的運算放進一次（或少數幾次）GPU 提交，就像 `train_step_device.js` 的整步路徑（`trainStepDevice`）那樣。它已經存在，但只涵蓋 LoRA 梯度；全參數版本是 P1 的下一項工作（缺口：基底權重 dW、嵌入梯度、RMSNorm 增益梯度，見 INVENTORY）。
- 估計：若一步只剩 2–3 次提交，每步開銷從 3 s 降到約 50–100 ms，再加上 GPU 矩陣乘本身，應能接近 cpu-py；這是估計，未實測。
