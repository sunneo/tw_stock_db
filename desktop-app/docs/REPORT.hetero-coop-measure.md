## 3. 解釋（剖析數字）

1. **cpu 側有很大的固定成本，不隨序列數線性增加。** L 規模：cpu 單一呼叫 4 序列時，牆鐘中位數 1633 ms、工作者中位數 965 ms，兩者差約 670 ms 是代理搬運（參數約 3M 個 f64，每步來回約 24 MB）。合作時 cpu 只分到 1 個序列，卻仍要 1140–1820 ms（工作者 880–1740 ms）。也就是 1 個序列的 cpu 呼叫幾乎和 4 個序列一樣慢。
2. **比例模型假設線性，所以份額會走偏。** 協調端的比例公式假設時間正比於序列數，但 cpu 側的固定成本讓它不成立。L 的份額從 0.58 一路推到 0.85（gpu 拿 3 序列、cpu 拿 1 序列），cpu 這一份變成關鍵路徑（約 1200 ms），合作總時間被它拖住。這正是設計文件 §2 的 `co`（固定成本）在實作裡沒有被量進去的後果。
3. **協調端自己的 AdamW 與梯度平均**：L 約 200 ms、M 約 60 ms（JS 的 fp64 更新 3M 個參數），這是純開銷。
4. **同機 CPU 競爭**：合作時 cpu 工作者與 Electron 渲染行程（cudaweb 的 JS 端）共用 4 個核心，cpu 的工作者時間在合作時比單獨時還長（L：1 序列 1140–1820 ms）。這一點沒有單獨量測來分開，只能列為可能原因。
5. **cudaweb 每步的 loadResident（把全部參數寫回裝置）**：L 的 gWall 818 對 gCompute 750 ms，約 70 ms 是寫入。M 的差距約 15 ms。

## 5. 結論與決定

- 合作在 M、L 不比單一資源快，L 還比單 cpu-py 慢；S 的優勢不足以下結論。**分攤維持預設關閉。**
- 要讓合作有機會贏，需要先：(a) 把 cpu 側固定成本（代理搬運、參數打包、梯度匯出、AdamW）降下來，最好讓參數不必每步整包搬運；(b) 比例模型加入固定成本項（設計文件 §2 的 `co`），讓 1 個序列的分配不會被算成划算；(c) 量測 cpu 與 cudaweb 同時執行時的互相干擾。
- 這次量測的 cpu 走的是 **localhost HTTP 代理**，不是產品的 Electron↔Python 橋接，所以 cpu 側的絕對數字不能直接套到產品路徑。
