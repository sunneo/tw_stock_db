## 3. 解釋（剖析數字）

1. **cpu 側有很大的固定成本，不隨序列數線性增加。** L 規模：cpu 單一呼叫 4 序列時，牆鐘中位數 1633 ms、工作者中位數 965 ms，兩者差約 670 ms 是代理搬運（參數約 3M 個 f64，每步來回約 24 MB）。合作時 cpu 只分到 1 個序列，卻仍要 1140–1820 ms（工作者 880–1740 ms）。也就是 1 個序列的 cpu 呼叫幾乎和 4 個序列一樣慢。
2. **比例模型假設線性，所以份額會走偏。** 協調端的比例公式假設時間正比於序列數，但 cpu 側的固定成本讓它不成立。L 的份額從 0.58 一路推到 0.85（gpu 拿 3 序列、cpu 拿 1 序列），cpu 這一份變成關鍵路徑（約 1200 ms），合作總時間被它拖住。這正是設計文件 §2 的 `co`（固定成本）在實作裡沒有被量進去的後果。
3. **協調端自己的 AdamW 與梯度平均**：L 約 200 ms、M 約 60 ms（JS 的 fp64 更新 3M 個參數），這是純開銷。
4. **同機 CPU 競爭**：合作時 cpu 工作者與 Electron 渲染行程（cudaweb 的 JS 端）共用 4 個核心，cpu 的工作者時間在合作時比單獨時還長（L：1 序列 1140–1820 ms）。這一點沒有單獨量測來分開，只能列為可能原因。
5. **cudaweb 每步的 loadResident（把全部參數寫回裝置）**：L 的 gWall 818 對 gCompute 750 ms，約 70 ms 是寫入。M 的差距約 15 ms。

## 5. 結論與決定

- 合作在 M、L 不比單一資源快，L 還比單 cpu-py 慢；S 的優勢不足以下結論。**分攤維持預設關閉。**
- 要讓合作有機會贏，需要先：(a) 把 cpu 側固定成本（代理搬運、參數打包、梯度匯出、AdamW）降下來，最好讓參數不必每步整包搬運；(b) 比例模型加入固定成本項（設計文件 §2 的 `co`），讓 1 個序列的分配不會被算成划算；(c) 量測 cpu 與 cudaweb 同時執行時的互相干擾。
- 這次量測的 cpu 走的是 **localhost HTTP 代理**，不是產品的 Electron↔Python 橋接，所以 cpu 側的絕對數字不能直接套到產品路徑。

## 6. 限制（如實列出）

- 只跑 1 次；每格 10 步；批次 4 序列（小）。
- 代理是測試用的，不是產品路徑。
- cudaweb 核心仍在另一個工作階段優化中；之後的數字要用新提交重測。
- 屋頂線採用 `scripts/bench/sizes.js` 的預設峰值（0.3 TFLOPS、14 GB/s），不是這張卡的實測峰值。

### 7.4 L 規模一步的剖析（第 1 次，逐步中位數）
- cudaweb 3 個序列：約 735 ms（計算 670 ms，寫回裝置 loadResident 約 30–60 ms）。
- cpu 1 個序列：430–1400 ms（工作者的 fwdBwd 370–1260 ms）。獨立量測同樣 1 個序列約 110–200 ms，所以**在 Electron 裡 cpu 側慢 3–4 倍**，主因是與渲染行程（cudaweb 的 JS 端與 GPU 驅動）搶同一台 4 核心。
- 協調端：AdamW 64 ms、加權累加 34 ms、範數 7 ms，合計約 105 ms，全部在關鍵路徑後面。

### 7.5 結論（對照使用者目標）
- 目標「合作優於單 cpu-py」：S 與 L 兩次都達成（L：701 對 959、775 對 1049；S：60 對 68、47 對 58）。**M 第 2 次不達成**（299 對 288）。
- 目標「接近理論 70 ms」：未達成。理論值用的是每序列速率（cpu 112 ms、cudaweb 189 ms）；以 K=4 計，理想合作約 290 ms，但本機 cpu 側在 Electron 裡慢 3–4 倍，理想值也只到 390–420 ms（L）。
- **與 cudaweb 單獨比：** 合作在 S、L 有時更快（L 第 1 次 701 對 744），有時更慢（L 第 2 次 775 對 620；M 兩次都慢）。在這台機器上，**cudaweb 單獨通常就是最快的路徑**，合作的收益被 cpu 側的爭用與協調端開銷吃掉。
- 依規定，合作在多數規模與多數次量測不優於最快的單一資源，**預設維持關閉**。

### 7.6 未做、需要的下一步
- 讓 cpu 側不與 cudaweb 爭核心（例如把 cudaweb 的 JS 工作與 cpu 工作錯開，或把 cpu 工作者放到獨立行程的核心親和性設定）：需要產品側的排程，本次不做。
- 協調端 AdamW 的 64 ms：可以改在 cpu 工作者端做（torch 的 AdamW 多執行緒，且參數不必回傳，只要每步同步梯度），需要重新設計參數流向；這是下一個設計題，不在這次的改善範圍。
- 產品路徑（Electron 主行程↔Python 橋接）的 cpu 側沒有量測；本報告的 cpu 數字是測試代理的，不能直接套用到產品。
