# 目標：這台 Kepler 上 WebGPU 矩陣乘趨近官方 cuBLAS 的效能

使用者 2026-11-18：「這台有 kepler 的 cuda 核心，要讓 webgpu 趨近官方的 cublas 一樣效能」。

## 這台的硬體與能不能直接量 cuBLAS（2026-11-18 查過）
- 顯示卡：NVIDIA GeForce GT 720（Kepler 第二代 GK208，一個 SMX、192 個 CUDA 核心、約 0.8 GHz、14 W 等級）。驅動 475.14，支援到 CUDA 11.4。
- **這台量不到真正的 cuBLAS**：裝的工具包是 CUDA 13.1（`nvcc` 在 `E:\Program Files\NVIDIA Corporation\CUDA SDK`），已不支援 Kepler（sm_35）；系統裡沒有 cuBLAS 動態庫；Python 有 numba 0.68 與 onnxruntime，沒有 torch／cupy。要量真的 cuBLAS 需要 CUDA 11.x 的 cuBLAS（例如 cu113 版的 PyTorch 或 CUDA 11 工具包），使用者若有再提供。
- 所以「趨近 cuBLAS」用**屋頂模型**來定義，不用猜 cuBLAS 的數字：
  - 理論峰值（規格推算，僅供參考）：192 核 × 2（乘加）× 約 0.8 GHz ≈ 300 GFLOP/s（fp32）。**以 WebGPU 內實測為準**：寫一個純 FMA 連鎖的核心量這張卡在 WebGPU 能達到的 fp32 峰值（`peakFlops`），再寫一個純複製核心量記憶體頻寬（`peakBW`）。
  - 已知參考：Kepler 上 cuBLAS SGEMM 一般可達峰值的 70% 到 80%（手工調過的組合語言等級核心）。
  - **目標：大矩陣乘（例如 512x1024x1024、512x1024x3072、1024x1024x1024）達到 WebGPU 實測峰值的 60% 以上（第一階段 40%）；記憶體受限的運算（解碼的 GEMV、逐元素）達到實測頻寬的 80% 以上。**
- 現況（`mm_ops.js` 平鋪核心，真 Chrome 同機）：512x1024x1024 約 33 ms ≈ 32 GFLOP/s ≈ 理論峰值的 10%；512x1024x3072 約 78 ms ≈ 41 GFLOP/s ≈ 13%。還有 5 倍以上的空間。

## 要做什麼（依預期收益排序；每一項都量「優化前後」）
0. **先量屋頂**：`peakFlops`（純 FMA）與 `peakBW`（複製）驗證頁，寫進 `scripts/eval/cudaweb_optimize.result.json`；之後所有核心都回報「峰值的百分之幾」。
1. **暫存器分塊加大**：每個執行緒算 8×8（甚至 8×4）輸出；工作群組 8×8 或 16×16 個執行緒；K 方向展開（常數迴圈）。Kepler 每個 SMX 有 65536 個暫存器、每個執行緒最多 255 個，8×8 分塊約用 100 個暫存器，要和同時駐留的群組數取捨（用實測選）。
2. **向量載入與合併存取**：A、B 用 `array<vec4<f32>>` 綁定，一次 128 位元；搬進共用記憶體時相鄰執行緒讀相鄰 16 位元組；A 的平鋪塊存成轉置（K 為主）讓計算時讀共用記憶體沒有 bank 衝突（Kepler 的共用記憶體有 4 位元組與 8 位元組兩種 bank 模式，WebGPU 不能選，用補位或轉置避開）。
3. **明確的 `fma()`**：WGSL 的 `a*b+c` 不保證融合成 FMA；內層乘加一律寫 `fma(a, b, c)`，量一次有沒有差。
4. **軟體管線（預取）**：先把下一個 K 平鋪塊讀進暫存器，計算這一塊的同時等記憶體，再寫進共用記憶體（這張卡沒有非同步複製，用暫存器暫存模擬雙緩衝）。
5. **K 方向切分（split-K）**：M、N 都小但 K 大時（解碼、LoRA），把 K 切給多個群組再歸約，才填得滿 SMX。
6. **工作群組大小與佔用率**：128、192、256 個執行緒各試；依 `maxComputeInvocationsPerWorkgroup` 與共用記憶體上限（16 KiB）算出合法的組合，交給自動調校（O9）在這張卡上選。
7. **貼圖／uniform 路徑**：上一棒實測「輸入向量放 uniform 慢約 8 倍，不採用」；貼圖放 B 的版本還沒量（O1m 的 (b)），按清單量，沒好處就如實記。
8. **同樣的做法套到 q8mm、MatMulNBits、注意力、卷積**（它們的內層也是乘加，用同一套暫存器分塊與向量載入）。
9. **訓練用的轉置版**（`AᵀB`、`ABᵀ`）共用同一份核心，只改索引。

## 規則
- 每個變體都要：CPU 參考對拍（相對誤差 ≤1e-6）、真 Chrome 驗證頁（照 `scripts/eval/mm_tiled_check.html`）、同機計時（標硬體、中位數、先暖機）、回報「GFLOP/s 與峰值百分比」。沒有量到好處的變體如實記「沒有好處」，不要留著增加複雜度。
- 不在真 GPU 上跑會逾時或卡死的測試（會讓 Chrome 的 WebGPU 消失）；單次派發太大要分批。
- 用完測試伺服器與分頁一定關掉並確認無殘留。
- 不宣稱「等於 cuBLAS」：只報我們量到的峰值百分比與 GFLOP/s；若使用者提供 CUDA 11 的 cuBLAS 才能做真正的並排比較。

## 變體階梯與預先剖析（使用者 2026-11-18 的設計想法）
使用者原話：「早期 cuda library 的一些 sample，會用 template programming 來訂好多層的 shared memory，會逐層切割 kernel function、device function，好幾個 device function 會特化成好幾個 2 的冪次方梯度優化過的小方塊切割，在編譯時期產生出來。我們有辦法優化出 runtime 準備多個冪次方梯度優化？然後預先準備好 pre-profile，幫不同能力的顯卡預選，即使不是 nvidia 架構。然後在 gpu 那頁 benchmark 挑出這種良好的成果。」

WGSL 沒有樣板，但有兩個對應做法：(1) 用 JavaScript 產生器把「大小參數」代入字串，產出一整族特化過的 WGSL（編譯時期特化的對應）；(2) 用 WGSL 的 `override` 常數，在建立管線時指定數值（可用在工作群組大小與共用記憶體陣列大小），同一份程式文字不必重產。兩者都在執行時期完成，所以「準備多個冪次方階梯」可行。

### 項目（併入優化清單，R1 之後做；每項要有 node 測試、真 Chrome 對拍與同機計時、安全量測規則）
- [ ] **G1. 核心產生器** `renderer/src/gpu/kernel_gen.js`：參數空間 `{ BM, BN, BK, TM, TN, 執行緒數, 向量寬度(1/2/4), 共用記憶體補位, K 展開, split-K, 精度(f32/f16) }`，各自取 2 的冪次（BM、BN ∈ {16,32,64,128}；TM、TN ∈ {1,2,4,8}；BK ∈ {4,8,16,32}）；`enumerate(caps)` 依能力表過濾合法組合（共用記憶體 ≤ `maxComputeWorkgroupStorageSize`、執行緒數 ≤ `maxComputeInvocationsPerWorkgroup`、暫存器用量估計 TM×TN 累加器＋行列暫存 ≤ 預算）；`generate(variant)` 回傳 WGSL（程式要短：內層 k 用迴圈、只展開 TM×TN 的 fma，避免把 Windows 的著色器編譯器拖慢）。同一個產生器覆蓋矩陣乘、q8mm、MatMulNBits（各自的內層不同，外層切割共用）。驗收：node 測試每個合法變體的 WGSL 通過「假裝置的結構檢查」（參數代入正確、陣列大小不超限、編譯期可算的整除關係成立）；CPU 參考對拍用假裝置的解譯版。
- [ ] **G2. 階梯預設與編譯預算**：挑出約 8 到 12 個代表性階梯（例如 32x32/t2x2、64x64/t4x4、64x128/t4x8、128x64/t8x4、128x128/t8x8、各加 vec4 與 split-K 版），每個管線編譯用 `createComputePipelineAsync` 並記錄編譯毫秒；單一變體編譯超過預算（預設 1500 ms，可調）就標「編譯太慢」並不再嘗試；編譯在背景做，不擋使用者操作。驗收：真 Chrome 逐個變體編譯時間與正確性表（在這張 GT 720 上）。
- [ ] **G3. 預先剖析表（priors）** `renderer/src/gpu/profile_priors.json`：鍵＝能力等級（由 O1 的能力表算出的簽名，例如「無 f16／無 subgroups／共用 16 KiB／256 執行緒」，不看廠牌）＋運算＋形狀區間；值＝候選變體的優先順序。內容分兩種並**明確標示**：`measured`（真機量過，現在只有這張 GT 720 的資料）與 `heuristic`（沒有機器可量的等級，由屋頂模型與佔用率估算：暫存器用量、共用記憶體用量、每個 SMX／CU 可同時駐留的群組數、算術強度）。不得把 heuristic 當成已量測的結果顯示。另提供「匯出我的剖析」與「匯入剖析」（JSON），讓使用者或維護者在別的顯卡（AMD、Intel、Apple）上量完把結果貼回來，併進 priors。驗收：node 測試涵蓋簽名計算、查表、heuristic 排序在三種假能力表上的結果合理；匯出入往返不失真。
- [ ] **G4. 執行時期選擇與驗證**：第一次用某變體前，先用小形狀對 CPU 參考做一次正確性檢查（不同廠商的驅動行為不同，不能只信 priors），不過就把該變體標壞並退回下一名；使用 priors 的第一名立刻開始工作；背景在時間預算內（≤2 秒、可取消、遵守安全量測規則）對前 K 名（預設 3）實測，勝者寫進本機快取（鍵含 adapter 描述與能力簽名，簽名變了就失效）；使用者可強制指定或恢復預設。驗收：node 假裝置測試涵蓋「優先名失敗退回、快取命中、簽名變更失效、強制覆蓋」；真 Chrome 在這台跑一次。
- [ ] **G5. GPU 設定頁的「變體競賽」基準**：在設定頁 GPU 基準（AI 助理設定與桌面版設定頁兩處同步，現有的 `bench_run.js`／`bench_core.js` 已有矩陣乘基準）加一張表：形狀 × 變體，欄位為 GFLOP/s、占實測峰值（R0 的屋頂）百分比、編譯毫秒、正確性、來源（measured／heuristic／本機實測），勝者標示；按鈕：「套用最佳」「重跑」「匯出剖析」「匯入剖析」「恢復預設」。基準本身要遵守安全量測規則（逐形狀、先估時間、分批、監聽裝置遺失、可取消）。驗收：node 測試涵蓋表格資料結構與按鈕行為（假裝置）；真桌面版／真 Chrome 開頁看一次實際畫面並讀 DOM（不要只信程式）。

### 修正（使用者 2026-11-18）：編譯慢沒關係，是一次功
「編譯慢沒關係，這通常是一次功，設備換了就再 benchmark，再編一次，可以存在 indexdb。」
- G2 的「編譯超過 1500 ms 就放棄」改為：**不因為慢而淘汰變體**。只留一個很寬的安全上限（例如單一變體 30 秒，只為防卡死），逾時才標壞。編譯時間照記、照顯示，但不當成淘汰理由。
- G4 的快取改存 **IndexedDB**（失敗時退記憶體）：鍵＝adapter 描述＋驅動／瀏覽器版本＋能力簽名；值＝各運算×形狀區間的勝者變體參數與量測結果。簽名或版本變了就自動重跑完整 benchmark 並重存。注意 WebGPU 的已編譯管線無法序列化，所以快取存的是「選哪個變體」，下次啟動只需編譯勝者那一兩個（很快），不必重編整個階梯。
- 完整階梯的編譯與量測放在背景或設定頁「變體競賽」按下去才跑；仍遵守安全量測規則（逐個、可取消、監聽裝置遺失）。
